# Round 4 re-review: consensus-engine replacement

Author: cx.astra. Date: 2026-09-25. **Verdict: REJECT.** The Round 3 revision makes useful corrections, but does not close all eight Round 2 blockers. Quorum membership, external-authority ordering, origin-sensitive migration, and phase-specific recovery still require substantive design decisions.

This is a design review against the actual revised text and source. Absence of the proposed implementation is not itself a reason for rejection. The reason is that materially different, incompatible implementations still satisfy the draft's words. This review adds only this document; no implementation/configuration change, activation, commit, or peer dispatch was performed.

**B1 — Ownership is clearer; the operation contract is still incomplete.**

The revision genuinely fixes the ambiguity over who owns the reducer, persistence, and retry instance. I accept those changes. However, `ConsensusEvent` and `EvalContext` are only names. The table is an owner inventory, not a definition of allowed source phases, event payloads, required evidence, injected time/IDs, terminal updates, or resulting transitions.

This matters at existing semantic forks. `mark_timeout()` records evidence and escalation while preserving the phase; the current stub's `process_timeout()` changes it to `forced_escalation`. The revised line 26 does not choose between them. Arbiter evidence currently requires a resolved round, verified dispatch, matching peer/profile, a valid parsed verdict and first-valid-reference-wins, without changing the decision. Revised line 30 mentions only identity/profile/verdict. See [consensus.py](../../peerhub/governance/consensus.py), lines 236-265, 641-764, 830-874.

**Required:** Add a compact per-event contract, or explicitly incorporate the exact existing predicates being preserved. Resolve the timeout phase choice; retain or deliberately replace the arbiter constraints; identify the ingress and evidence for general/exceptional resolution and retraction. Define the frozen context fields needed for deterministic evaluation. This does not require implementation code or a new workflow framework.

**B2 — The port and whole-electorate rule are accepted; the four-way credential contract is not actually written out.**

Revised line 41 correctly fixes optional-but-present invalid credentials. Line 42 rejects a missing verifier when verification is required. It does not state what happens when a verifier exists but a required credential is absent. Nor does it explicitly preserve the optional/absent asserted path. The existing rule is precise: presented proof must verify; otherwise reject iff `verified_required` is true. Eligibility is checked separately. See [consensus.py](../../peerhub/governance/consensus.py), lines 166-177 and 544-569; [governance_authorizer.py](../../peerhub/application/governance_authorizer.py), lines 10-18 and 54-73.

The live predicate at revised lines 45-48 also omits the prerequisite of an existing, well-formed registry node and a nonmissing health projection. The source returns false for a missing node/projection and rejects malformed identity; it then checks availability, admission and backoff. See [proposals.py](../../peerhub/application/proposals.py), lines 172-205. None of those observations by itself authenticates the caller.

**Required:** State optional+absent -> asserted path; required+absent -> reject regardless of verifier availability; present -> verify against the claimed actor or reject, including when no verifier exists. Add registry/projection failure dispositions, frozen membership checks, and separately validated exceptional authority. Define whether “entire required electorate” means `participants.required`, `participants.eligible`, `required_acks`, or a named frozen authority set: current proposal reconciliation checks every **eligible** voter, and legacy Final Call also uses **eligible** membership. See [proposals.py](../../peerhub/application/proposals.py), lines 604-630; [consensus.py](../../peerhub/governance/consensus.py), lines 166-205. The composition-root port itself is the correct direction. Commit-time ordering is B5.

**B3 — Copying the four formulas does not solve proposer counting or the binding minimum.**

Revised lines 59-62 accurately copy the orchestrator arithmetic for valid inputs. They still do not define `total_voters`, `N`, whether the proposer is already included, which set supplies `agree_count`, or how the service's required/eligible identities map into those inputs. Proposal creation passes the same eligible tuple as both required and eligible, and that tuple can include the proposer. See [proposals.py](../../peerhub/application/proposals.py), lines 280-294; [consensus.py](../../peerhub/governance/consensus.py), lines 79-105.

**[empirical_probe]** The current [orchestrator](../../peerhub/dispatch/orchestrator.py), lines 48-77, returned:

| Inputs | Result | Unresolved implication |
|---|---|---|
| `total_voters=3`, proposer voted, three agreements, `unanimous` | `pending` | Passing the full three-person set double-counts an included proposer. |
| `total_voters=1`, proposer voted, two agreements, `unanimous` | `check_final_call` | Revised line 65's blanket “N=1 ... unanimous is impossible” does not follow from line 62. |
| `total_voters=1`, one agreement, majority/supermajority/all_required | `check_final_call` for each | “Strict math” does not enforce the binding minimum of two. |

The first example is not an objection to preserving tested arithmetic; it demonstrates why an explicit membership adapter is necessary. The latter examples require defining whether `N` counts the complete electorate or excludes a distinct proposer. Revised line 103 only states non-proposer agreement for proposal-type rounds, leaving native binding rounds unresolved. The previously ratified contract freezes logical identities, denominator, required membership and independence, and distinguishes advisory REVIEW from binding minimum-two consensus: [ratified revision](GOVERNANCE-DISPATCH-R4-revision-ag-deepthink-2026-09-24.md), lines 94-97.

The correction-event sentence is useful but does not define same-command duplicates, unauthorized changed votes, old-contribution invalidation or candidate consequences. Ordinary dissent versus typed blocking concern is also still unspecified here; today's service vetoes any disagreement. See [consensus.py](../../peerhub/governance/consensus.py), lines 577-626, and the [ratified correction/dissent rules](GOVERNANCE-DISPATCH-R4-revision-ag-deepthink-2026-09-24.md), lines 94-100.

**Required:** Define one frozen identity/set/count contract, a proposer-included/excluded adapter, the binding floor and independence across applicable native/proposal paths, duplicate validation, and dissent/correction dispositions. Correct the N=1 statement. Demonstrate the adapter with proposer-inside/outside and one/two/three-person examples; do not merely restate the arithmetic.

**B4 — Snapshot storage and monotonicity are accepted; policy selection is still undefined.**

Revised lines 73, 77 and 81 close real subissues: persist effective policy, never downgrade unanimity, and deliberately change unreadable-config handling. The loader tightening is a proposed change, not current behavior: [policy_resolver.py](../../peerhub/dispatch/policy_resolver.py), lines 21-37, still returns `{}` on read `OSError`, which the injected probe confirmed **[empirical_probe]**.

The remaining gap is concrete wiring. `resolve()` takes no risk input; an action override only changes consultation depth, while consensus policy remains shared. `DispatchOrchestrator.evaluate()` currently ignores its policy/action/risk arguments. Revised “QUORUM or UNANIMOUS” still leaves the floor choice open. See [policy_resolver.py](../../peerhub/dispatch/policy_resolver.py), lines 61-76 and 112-148; [orchestrator.py](../../peerhub/dispatch/orchestrator.py), lines 9-25.

No schema defines snapshot version, validated fields, identity/hash, decoding, unsupported values, or effective action/origin policy. The current resolver returns `source_hash="000"`; the frozen policy contains a mutable routing dictionary. Serialization can solve this, but the draft must specify the authoritative saved representation and validation. See [policy_resolver.py](../../peerhub/dispatch/policy_resolver.py), lines 217-228; [policy.py](../../peerhub/dispatch/policy.py), lines 28-30 and 46-73.

**Required:** Define risk inputs and the exact monotone floor, per-action consensus-policy selection, and the versioned stored policy contract. Explicitly carry the mandatory `tier-0 OR high-risk OR unresolved dissent` union and retained dissent-origin obligation after disposition, rather than depending on an unexplained boolean. Freeze configuration once, while specifying how later votes/concerns update obligations under that frozen policy. Define restart decoding and reject inconsistent snapshots. See the [ratified revision](GOVERNANCE-DISPATCH-R4-revision-ag-deepthink-2026-09-24.md), lines 99-100; [consensus.py](../../peerhub/governance/consensus.py), lines 831-841.

**B5 — Atomic state/effect persistence is fixed; authority and retraction are not serialized by that fix.**

Revised line 91 correctly restores construction of the approval and effect before the single broker transaction. This closes the specific Round 2 commit-order regression. Candidate-bound ACK storage, fresh CAS evaluation and caller-supplied revision conflicts are also useful explicit changes.

But the shell's revalidation at line 50 still has no shared transaction/version fence with authority changes. A permitted schedule remains: read round revision R and open gates; another transaction closes a required voter or revokes/rebinds authority without changing R; submit approval at R. The existing broker validates the round revision, commits state/receipt/outbox, and has no dependency-version predicate for that authority change. Its effect claim checks delivery ownership/state, not current authorization/revocation. See [broker.py](../../peerhub/governance/broker.py), lines 311-420 and 504-552; [contract.py](../../peerhub/governance/contract.py), lines 247-260. This is a source-based counterexample to the proposed ordering, not a claim of an observed production race.

The missing design is the one already required in Round 2: a named transactional or version-fenced authorization interface and a common ordering for authorization, revocation and claim. The [ratified contract](GOVERNANCE-DISPATCH-R4-revision-ag-deepthink-2026-09-24.md), lines 100, 126 and 133-136, expressly requires it. A pure reducer cannot supply it by itself.

Candidate fields alone also leave unspecified: what identifies the candidate, what changes invalidate all ACKs or require fresh votes, which concerns block, which phases accept ACK/NACK/retraction, what proof permits an exceptional decision, and how pre-authorization retraction differs from post-authorization revocation. There is still no assigned public event entrance for these operations.

Finally, line 94's stable mutation ID is a necessary direction, but insufficient with the existing broker. Its semantic digest includes `expected_revision`, the entire desired state and effect payload; the same key with a recomputed timestamp/revision produces a mismatch. This was reproduced **[empirical_probe]**. See [mutations.py](../../peerhub/governance/mutations.py), lines 33-59; [broker.py](../../peerhub/governance/broker.py), lines 319-348; [contract.py](../../peerhub/governance/contract.py), lines 331-349. After response loss, replay must find the original receipt before attempting a now-invalid phase transition, or reuse the original bound request.

**Required:** Specify the authorization dependency/fence inputs and commit/claim checks, exact candidate invalidation and exceptional-resolution predicates, public ACK/NACK/retraction events, and the durable semantic-command-to-receipt binding. Establish both serial orders for last ACK/retraction and authority-change/authorization in the acceptance design. Preserve explicit stale preconditions. Do not split approval and effect into separate commits while adding these guards.

**B6 — Proposal ownership is improved; its policy and completion route remain incomplete.**

I accept the explicit preservation of the three escalation reasons and independent agreeing voter at revised lines 102-103. I also accept the requirement at line 106 to include `RATIFIED_INVARIANT_EFFECT_KIND` in the final approval transaction on both immediate and Final Call paths.

However, “explicit policy dispositions” at line 101 supplies no dispositions. The current full priority is resolved recovery -> existing escalation -> too few eligible voters -> any eligible gate closure -> eligible dissent rejection -> all required agree plus independent agreement -> proposer-only self-finalization escalation. See [proposals.py](../../peerhub/application/proposals.py), lines 555-691. The draft preserves the ordering of the three escalations, but does not resolve their interaction with dissent, mandatory Final Call or reopening, or specify the proposal's effective quorum/final-call policy. A global majority policy must not silently replace the proposal's unanimous/reject-on-dissent behavior without a stated intentional change.

High-risk proposal Final Call changes current auto-resolution and needs an ingress that can complete it and trigger the same invariant materializer after restart. Current native handlers expose proposal create/vote and consensus propose/vote/read/sweep; they do not expose the candidate-bound ACK/NACK/retraction events being designed. See [handlers/consensus.py](../../peerhub/application/handlers/consensus.py), lines 100-174 and 208-293. Naming a reducer does not connect those callers.

Effect-kind ownership needs an explicit exclusion as well: today's generic `process_consensus_effects()` can claim any matching non-noop round event and mark it successful. The invariant projector alone materializes the exact immutable target before recording success. Merely retaining that projector does not prevent the generic worker from consuming its event. See [consensus.py](../../peerhub/governance/consensus.py), lines 486-525; [invariant_requests.py](../../peerhub/governance/invariant_requests.py), lines 128-165. The revised ownership table points in the right direction but has no concrete routing/failure rules.

**Required:** Supply the proposal policy dispositions and full precedence, identify high-risk Final Call as an intentional change, and map its native ACK/recovery entrance. Specify how the bounded effect factory receives the final approved snapshot/revision before submission without introducing an upward core dependency. Route each effect kind exclusively to its materializer, hold/error on unknown kinds, and preserve `CONSENSUS_OK`, `NACK`, `ESCALATED`, request ID and exactly-one-target recovery. The payload and recovery requirements already exist at [proposals.py](../../peerhub/application/proposals.py), lines 344-490 and 508-552.

**B7 — V1/V2 is schema provenance, not action/origin provenance.**

The new version tags and removal of `verified_required`/text guessing are accepted. The missing origin problem remains unchanged: both creation paths call the same constructor and store `peerhub.consensus-round.v1`. With fixed time/IDs and matching public inputs, actual `add_proposal()` and direct `propose()` produced equal entire state envelopes **[empirical_probe]**. See [proposals.py](../../peerhub/application/proposals.py), lines 236-294; [consensus.py](../../peerhub/governance/consensus.py), lines 82-127.

The new schema declaration also contains no explicit origin/action discriminator. Yet section 6 needs that discriminator to select proposal predicates and the invariant effect instead of a generic decision. Section 8's “ambiguous origin” test category is not a rule for handling ambiguity.

The adapter says it freezes historical `max(2, N)` without defining N, the fixed-count representation understood by the single evaluator, or which stored count is authoritative when `participants.quorum.required` and `quorum.required_votes` disagree. Current voting uses the latter; current policy has no fixed-count field. See [consensus.py](../../peerhub/governance/consensus.py), lines 101-115 and 588-616; [policy.py](../../peerhub/dispatch/policy.py), lines 14-18. Removing the unsupported `custom` string is correct, but naming a “validated quorum contract” does not define it.

The “every entrypoint” intent at line 118 is accepted; implementation mapping must include broker-backed proposal list/recovery enumeration, not just the five named service methods. Those bypass `ConsensusService.get_target()`: [handlers/consensus.py](../../peerhub/application/handlers/consensus.py), lines 195-204; [proposals.py](../../peerhub/application/proposals.py), lines 693-708.

**Required:** Add validated V2 origin/action fields and a V1 provenance source or explicit migration mapping; hold ambiguous records for a documented disposition. Do not infer origin from the schema tag. Specify the legacy fixed-count contract, count/identity consistency checks, unknown/missing/inconsistent schema failures and every read/mutation/recovery adapter path. Preserve historical hashes, receipts and original approval identity without pure-read writes. B8 covers terminal and in-flight disposition.

**B8 — A cutover choice and coverage axes are present; a complete cutover contract is not.**

Revised line 129 does make two choices: drain/fence old writers and retain unbound ACKs under a legacy evaluator. These are permitted directions from Round 2. But preservation was conditional on a **demonstrably equivalent frozen legacy contract**. The draft does not define that contract, what freezes its candidate/content/policy/electorate, how it interacts with new mandatory floors, or which event may complete it. Legacy ACKs contain only actor, boolean, time and mutation ID; completion uses the eligible set. See [consensus.py](../../peerhub/governance/consensus.py), lines 179-205. A different evaluator does not establish equivalence merely by retaining the old ACK map.

The other cutover phases appear only as test-axis labels. There is no migration/recovery disposition for proposed/voting, quorum reached, escalation/timeout evidence, resolved pending/claimed/completed effects, abandoned rounds or subsequent arbiter evidence. This matters especially because proposal recovery compares the request's `approved_revision` to the current round revision and its participants/votes to the round snapshot. Arbiter attachment increments that revision. See [proposals.py](../../peerhub/application/proposals.py), lines 448-485; [consensus.py](../../peerhub/governance/consensus.py), lines 714-759. “Preserve hashes” and “reads do not write” do not settle later evidence updates or transformed snapshots. The design must anchor recovery to immutable approval evidence or explicitly define another compatible validation rule.

The writer fence is also only a statement of intent. The current generic broker does not reject a consensus write based on round schema or writer generation; it accepts the caller's next state after CAS. See [mutations.py](../../peerhub/governance/mutations.py), lines 83-105. Define a stop/drain/exclusive activation procedure that covers all writers and stale processes, or an enforced writer-generation gate. A rolling CAS conflict alone is not that gate.

Finally, lines 134-142 reproduce the Round 2 axis matrix but do not expand it into concrete rows with preconditions, event order, expected revision/receipt and effect count as Round 2 required. They are a useful coverage checklist, not evidence of MECE cases or closure. Production construction still instantiates the legacy service/coordinator, and the new classes occur only at their definitions in the inspected `peerhub/` search. See [runtime.py](../../peerhub/runtime.py), lines 215-227 and 358-376. This is expected before implementation; the missing deliverable is the design's call-path-to-replacement mapping, not prematurely passing implementation tests.

**Required:** Add one phase-to-disposition table and an enforceable activation/fencing procedure. Specify how retained legacy ACKs remain equivalent; otherwise reopen/recollect or hold by an explicit migration decision. Cover pending/claimed/applied/completed effect recovery and post-resolution evidence without changing the approved identity. Expand the decisive coupled cases, including proposer counting, missing credential with installed verifier, authority change before commit, last ACK/retraction, origin ambiguity, terminal approval plus later arbiter attachment, and old-writer cutover, with expected durable records and effect counts. Map native/direct/proposal/recovery callers to the single evaluator and their adapters.

**Ratification gate**

Retain the revised architecture and the accepted fixes above. The next revision needs explicit membership/policy/event contracts, a fenced authority transaction, origin-safe adaptation, proposal effect completion, and phase-specific cutover dispositions. Those choices can be expressed compactly; repeating that they are “validated,” “atomic,” “preserved,” or covered by a matrix does not make the choices.

**Final vote: REJECT as written.** This is not a clean ratification with editorial amendments: the unresolved choices can change who approves, whether an unauthorized effect starts, which effect is produced, and whether an in-flight or already-approved round can recover.
