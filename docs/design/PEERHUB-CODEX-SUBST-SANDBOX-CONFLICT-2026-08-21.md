# Codex CLI dispatch failure on SUBST-mapped drives with special characters in the real path

Status: root-caused 2026-08-21, config-level mitigation applied to legacy `hub.py` (`P:\_sys\ai\infra.json`), design implication for peerhub's own `CodexAdapter` documented below, not yet implemented in `peerhub/adapters/codex_adapter.py`.

## Finding

Every `hub.py ask --to cx` dispatch that required Codex to spawn its own subprocess (reading a file, running `git`, executing extracted Python — i.e. any real, non-trivial review task) failed with a bare `exited 1` and no reply, six consecutive times across Rounds 66 of the Phase 1 admission dialectic in this same session. A minimal no-subprocess prompt ("reply OK") succeeded instantly every time. This pattern — trivial prompts succeed, anything requiring real work fails — pointed away from a quota/auth/connectivity problem and toward something specific to Codex's own subprocess execution path.

Direct invocation of `codex.cmd` (bypassing `hub.py` entirely) reproduced the failure and surfaced the real error:

```
ERROR codex_core::tools::router: error=exec_command failed for `powershell.exe -Command "git -C 'P:\workspace\peerhub' status --short"`:
CreateProcess { message: "UnsupportedOperation(\"windows unelevated restricted-token sandbox cannot enforce split writable root sets directly; refusing to run unsandboxed\")" }
```

**Root cause**: `P:\` is a `SUBST` virtual drive (`subst` output: `P:\: => D:\Engram&Peerhub\PortableDev (v2.1)`). Codex CLI's Windows sandbox (an unelevated restricted-token / job-object model) resolves the process's working directory to its real underlying NT path, and separately holds trust/config entries for both the `P:\` alias and several `D:\...` physical-path variants (see `P:\_sys\codex\config\config.toml`'s `[projects]` table). When both the SUBST alias and its real target are in play for the same physical location, the sandbox cannot express "this one location is a single writable root" through Windows' restricted-token mechanism — it sees two roots aliasing one place and refuses to run **any** subprocess at all rather than risk enforcing the wrong permission set. This is a genuine Codex-CLI-side Windows sandboxing limitation, not a bug in `hub.py` or `peerhub`.

**Why `P:\` (SUBST) is used at all, and why the fix isn't "just use the real path"**: the real underlying path contains a literal `&` character (`D:\Engram&Peerhub\PortableDev (v2.1)`), which Windows `cmd.exe`/batch-file argument parsing treats as a command separator. Invoking anything through the real `D:\` path breaks unless every layer in the chain quotes it perfectly — confirmed directly in this investigation: dispatching through the real `D:\` path caused Node.js's own `require()` to receive a silently truncated path (`Cannot find module 'D:\Engram\node_modules\@openai\codex\bin\codex.js'` — everything after `&` was lost), because some layer in the invocation chain built an unquoted command string. `P:\` is the existing, deliberate workaround for that `&`-in-path problem (see `hub.py`'s own comment-free but clearly intentional exe-path rewrite at `hub.py:6743-6759`, which converts a resolved real `D:\...` executable path back to a `P:\`-relative one specifically to avoid this). So the system is caught between two failure modes: the real path breaks naive command-line parsing, and the SUBST alias breaks Codex's own sandbox. Renaming the real directory to remove the `&` would resolve both at the root, but is out of scope for this investigation (a filesystem-level change to shared infrastructure, not a dispatch-adapter fix) and was not something the user authorized in this session.

**Confirmed not to affect other peers**: `ag` (agy.exe) has no filesystem-level OS sandbox at all (already documented in this project's own operating notes — its PTY has no FS sandbox), so it has no equivalent "split writable root" check and dispatches successfully from `P:\` with real subprocess execution (verified directly: a `git status --short` dispatch through `hub.py ask --to ag` succeeded normally). This is specifically a Codex-CLI Windows-sandbox behavior.

## Mitigation applied to legacy `hub.py` (this session, 2026-08-21)

`P:\_sys\ai\infra.json`'s `tool_paths.cx.default_flags` changed `--sandbox workspace-write` to `--sandbox danger-full-access`, confirmed directly (manual `codex.cmd ... --sandbox danger-full-access` invocation from `P:\` succeeded, including a real `git status --short`) to eliminate the conflict entirely. This is judged safe in this system specifically because `hub.py`'s own governed-mutation and capability-lease machinery is the actual security boundary around what a dispatched peer may do — Codex's own OS-level sandbox is a redundant, secondary layer here, not the primary one — so removing it for `cx` specifically does not remove the real enforcement. This mitigation was applied narrowly to `P:\_sys\ai\infra.json` at the user's explicit direction after the default auto-mode classifier correctly flagged it as a safety-relevant change requiring confirmation (it globally disables an AI-driven subprocess's own OS sandbox, which is a real trade-off worth a deliberate decision, not something to apply silently).

## Design implication for peerhub's own `CodexAdapter`

`peerhub/adapters/codex_adapter.py`'s `argv` construction (around lines 320-333) currently builds `("codex.cmd", "exec", "--json", prompt)` with **no explicit `--sandbox` flag at all**, meaning it inherits whatever `sandbox_mode` is set in the operator's `config.toml` (`workspace-write` in this environment). This means production peerhub, once it is actually driving real dispatches, will hit this exact same "cannot enforce split writable root sets" failure the moment it operates from any SUBST-mapped (or similarly aliased — e.g. a Windows drive-letter mapped network share, a junction with a differently-cased spelling, or a Docker/WSL bind-mount reachable by two different host paths) workspace root, with the same symptom profile: trivial prompts succeed, real work silently fails with no diagnostic pointing at the actual cause.

Recommendation, not yet implemented (Phase 2 scope, requires its own design/test cycle like every other adapter behavior in this project — not something to bolt on without the same scrutiny given to the admission-schema work):

1. **Detect the specific failure, don't just report a bare non-zero exit.** Codex's stderr for this condition is a distinctive, greppable string (`"cannot enforce split writable root sets"` / `UnsupportedOperation`). The adapter's decoder should recognize this pattern and surface a clear, actionable error (naming the SUBST/alias conflict) instead of an opaque `exited 1`, which is what cost this session six blind retries before the real cause was found by bypassing the adapter entirely.
2. **Do not default to `danger-full-access` silently.** Whatever this project's real recursive-derivation-of-workspace-identity logic ends up being (a natural companion to the Phase 1 admission design's own `AdmissionCoordinator`/`HostCapabilityInventory` work — both are fundamentally about establishing genuine, non-aliased identity for a filesystem location before trusting operations against it), the adapter should only escalate past `workspace-write` when it has positively detected an alias conflict it cannot otherwise resolve, and should log why, exactly as this session's manual `infra.json` change was deliberate and explained rather than silent.
3. **Prefer resolving to a single canonical root over sandbox escalation, where possible.** If the adapter can detect that its `cwd_reference`/`workspace_scope` is a SUBST/junction alias with a clean (special-character-free) real target, invoking Codex from the real path is the more honest fix — the sandbox conflict disappears entirely without weakening any security boundary. Sandbox escalation should be the fallback specifically for the case demonstrated in this investigation: the real path itself is not cleanly invokable (contains shell metacharacters), so neither the alias nor the real path can be used safely as-is.
4. **Cross-reference `HostCapabilityInventory`/`ProvisioningEvidenceReceipt`** (`PHASE1-ENGRAM-BRIDGE-INTERFACES-V2-2026-08-20.md`) and the Phase 1 `AdmissionRegistry`'s `canonical_path`/`os.path.samefile()` discipline (`PHASE1-PROMOTION-SCHEMA-V1-2026-08-20.md`, Rounds 47-65) — that work already had to solve an adjacent problem (never trusting a caller-supplied path string; always resolving to real, canonicalized filesystem identity before hashing/admitting). The same discipline — resolve to genuine filesystem identity before deciding how to invoke a peer CLI — is directly applicable here and should not be re-invented independently when Phase 2 implementation reaches this adapter.

## Process note

This was found mid-dialectic, while Round 66 of the Phase 1 `AdmissionRegistry` adversarial review (cx re-reviewing commit `87fe6d7`) was blocked by exactly this failure. Six consecutive `hub.py ask --to cx` attempts failed (profile-pinned to both `cx.deepthink` and `cx.effort`, across multiple freshly-named query files, after `peer-recover`) before the terminal stopped blindly retrying and instead reproduced the failure by invoking `codex.cmd` directly, per this project's own established discipline of never trusting a peer-dispatch failure without independently reproducing it outside the wrapper.
