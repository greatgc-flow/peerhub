**Target:** PeerHub SQLite Schema v2 unified migration framework.

## 1. Agreed Core Tenets & Contracts
- **Cross-Client Version Gate:** Released binaries (v0.16.0, v0.18.x) check only `PRAGMA user_version` (`peerhub/core/schema_version.py:8`, `peerhub/core/store.py:149-156`, `peerhub/core/migrations.py:185,202`). Bump `PRAGMA user_version` from 3 to 4. Older binaries halt immediately with their compiled `future_schema_message` (`schema_version.py:15-18`). Old binaries cannot emit dynamic backup paths; path guidance is emitted exclusively by v2 binaries and documentation.
- **Informational Migration Ledger:** `schema_migrations` table `(id INTEGER PRIMARY KEY, applied_at TEXT NOT NULL, component TEXT NOT NULL, checksum TEXT NOT NULL, version INTEGER NOT NULL)` is written within the migration transaction as an internal audit log. It is never queried by released clients.
- **Single Migration Owner:** Extension constructors must stop executing DDL. Replace scattered imperative init in `Bridge.__init__` (`peerhub/extensions/bridge.py:398-420`), `bridge_registry.py:101-135`, and `observation.py:44-65` with a single migration registry managed by `peerhub.core.migrations` during `Store` open. Extension constructors only assert schema compatibility.
- **Static Trigger Definition:** Bridge triggers (`bridge_delivery_session_immutable`, `bridge_result_write_once`, `peerhub/extensions/bridge.py:409-417`) are created once in versioned migrations; `Bridge.__init__` no longer drops and recreates triggers on open.
- **Connection Factory & FK Enforcement:** Central factory enforces `PRAGMA journal_mode=WAL`, `busy_timeout=5000`, `foreign_keys=ON`, and `recursive_triggers=ON`. Every connection checkout asserts `PRAGMA foreign_keys == 1`.
- **AST INSERT Lint:** Static AST checker (`test_ast_forbid_positional_inserts`) scans all SQL statements, rejecting positional writes in `INSERT INTO`, `INSERT OR IGNORE INTO`, `INSERT OR REPLACE INTO`, and dynamic SQL builders.
- **Relational Constraints:** Enforce `NOT NULL` on all TEXT PKs; real `REFERENCES` FKs across bridge tables; unique indexed `delivery_seq` in `bridge_deliveries` (`peerhub/extensions/bridge.py:238`).
- **JSON Field Promotion:** Promote query-critical fields to explicit typed columns while preserving domain semantics:
  - From `bridge_evidence.detail` (`peerhub/extensions/bridge.py:244`): nullable `session_handle` (TEXT, indexed), nullable `call_seq` (INTEGER), nullable `telemetry_seq` (INTEGER), nullable `started_monotonic_ns` (INTEGER), nullable `terminal_monotonic_ns` (INTEGER), nullable `monotonic_domain` (TEXT), and nullable `terminal_at_utc` (TEXT). Monotonic ticks are strictly kept as integer nanoseconds, never converted to UTC.
  - From `observations.payload_json` (`peerhub/extensions/observation.py:51`): nullable `pool_id` (TEXT, indexed), `kind` (TEXT NOT NULL), `observed_at_utc` (TEXT NOT NULL, indexed), nullable `captured_at_utc` (TEXT), nullable `freshness_ttl_sec` (INTEGER), and nullable `resets_at_utc` (TEXT). Heterogeneous telemetry payloads remain versioned JSON (`payload_version`).
- **Lifecycle Semantics & Retention:** `bridge_session_history` (`peerhub/extensions/bridge_registry.py:16`) is formally modeled as mutable lifecycle state (status, watermarks, tombstones); event ledgers remain strictly append-only. Telemetry TTL expiry in read models is evaluation-only, never authorization for automatic row deletion. Data retention/archival runs exclusively via an explicit maintenance command (`peerhub db prune`).
- **Checkpoint Policy:** No unconditional shutdown checkpoints. `PRAGMA wal_checkpoint(TRUNCATE)` is an explicit administrative action; routine runtime connections use standard WAL passive recycling.

## 2. In-Place Migration Sequence in WAL Mode (PROPOSED Consensus)
The executable migration workflow coordinates an exclusive migration connection `M` and a snapshot reader `R`:
1. **Connection Setup & Precheck:** Open migration connection `M`. Execute `PRAGMA synchronous = FULL` and `PRAGMA foreign_keys = OFF` (must be set outside transaction before `BEGIN`; SQLite ignores `foreign_keys` toggling inside a transaction, and active `foreign_keys = ON` would cascade-delete child rows like `stream_members` during parent-table drop/rebuild per `peerhub/core/migrations.py:42-44`). Run disk-space precheck asserting space for backup and WAL journal growth.
2. **Writer Fence Acquisition:** On `M`, execute `BEGIN IMMEDIATE`. This write lock constitutes the unbroken writer fence; concurrent writers encounter `SQLITE_BUSY` and wait up to `busy_timeout` (resuming normally if migration commits before timeout, or failing with a clean "migration in progress" error only if timeout expires). Hold this lock through `COMMIT`.
3. **Consistent Snapshot Backup:** Open separate read connection `R`. In WAL mode, `R` reads the last committed pre-migration snapshot consistently without interfering with `M`'s write lock. Stream backup using the SQLite backup API (or `VACUUM INTO` on `R`, never on `M`) to `peerhub.db.backup.<tmp>.tmp`. Verify the file (`PRAGMA integrity_check`, row counts, stream digests), `fsync`, and atomically rename (`os.replace`) to `peerhub.db.pre-v2.<timestamp>.bak`. If verification fails, abort, perform explicit `ROLLBACK` on `M`, unlink temp files, and release. (Tables declare explicit integer PKs so logical copy cannot shift rowids).
4. **Migration & Rebuild:** On `M` within the active transaction:
   - Run ordered migrations (core, extension DDL, table rewrites, static trigger creation).
   - Rebuild all derived projection tables.
   - Validate referential integrity and constraints (`PRAGMA foreign_key_check`, invariants).
   - Insert execution records into `schema_migrations`.
   - Execute `PRAGMA user_version = 4` as the final statement.
   - Execute `COMMIT`.
5. **Exception & Crash Semantics:**
   - Application exceptions require explicit `ROLLBACK` on `M` (not universally automatic across drivers/runtimes).
   - Process crash or power loss before `COMMIT` leaves WAL uncommitted; SQLite crash recovery automatically discards uncommitted frames on reopen, preserving `user_version = 3`.
   - *Pragma Transactionality Caveat:* In SQLite, `PRAGMA user_version` and table DDL are transactional; `PRAGMA synchronous`, `PRAGMA journal_mode`, and `PRAGMA foreign_keys` are non-transactional and must be configured outside transactions.
6. **Fence Release & FK Restoration:** Restore `PRAGMA foreign_keys = ON` on `M` after `COMMIT`, close connection `M`, and release write lock.

## 3. Preservation List & Source Attribution
The following structures are preserved without data loss:
- **Ledger Records, Peers & Streams:** Peers (`peerhub/core/migrations.py:21`); full Record payloads, timestamps, relationships, record IDs, stream positions, content digests, and idempotency keys (`migrations.py:46`); stream definitions and memberships (`migrations.py:29,38`).
- **Stream State:** Offsets, consumer group watermarks, and stream revisions (`migrations.py:67`).
- **Bridge Operations & Evidence:** Bridge deliveries and execution uncertainty (`peerhub/extensions/bridge.py:238`); raw bridge evidence (`bridge.py:244`); reconciliations, controls, and invocation resolutions (`bridge.py:251,253,322`); claim generations and finalizations (`peerhub/extensions/bridge_claims.py:50,61`).
- **Observation Store:** Resource pools and observation events (`peerhub/extensions/observation.py:45,51`).
- **Session Identity:** Session handles, generation counters, active watermarks, and tombstones (`peerhub/extensions/bridge_registry.py:12-24`).
- **Lineage & Artifact References:** Workspace lineage (`peerhub/core/workspace.py:99`); CAS artifact references recorded in work items (`ext_work_items.artifacts_json`, `peerhub/extensions/work.py:103`).

## 4. Downgrade Policy & Client Refusal
- Downgrade is **unsupported**.
- Older released binaries inspect `PRAGMA user_version` on connect (`peerhub/core/store.py:150-155`, `peerhub/core/migrations.py:202`). When `user_version = 4` is encountered, they refuse cleanly with their compiled error message (`peerhub/core/schema_version.py:16-18`).

## 5. RED Test List
- `test_released_binary_refusal_existing_guard`: Executes a fixture matching v0.16.0/v0.18.x refusal code against a v2 store (`user_version=4`), asserting clean refusal with `SchemaVersionError`.
- `test_bridge_init_does_not_mutate_schema`: Asserts opening `Bridge` performs zero DDL, does not drop/recreate triggers, and leaves `sqlite_master` trigger checksums identical.
- `test_ast_forbid_positional_inserts`: Static AST analyzer fails if any `INSERT`, `INSERT OR IGNORE`, `INSERT OR REPLACE`, or dynamic SQL string lacks an explicit column list.
- `test_connection_factory_foreign_keys`: Asserts `PRAGMA foreign_keys == 1` across all connections spawned by the central factory.
- `test_backup_atomic_rename_verification`: Interrupted backup leaves no corrupted target `.bak`; verified backup matches integrity check, row counts, and stream digests.
- `test_concurrent_writer_refusal`: Verifies writer fencing under `BEGIN IMMEDIATE` rejects or suspends concurrent writers until commit or timeout.
- `test_child_rows_survive_parent_table_rebuild`: Asserts child rows (e.g. `stream_members` referencing `streams`/`peers` via `ON DELETE CASCADE`) survive a parent-table rebuild with identical row counts and digests under `foreign_keys=OFF`.
- `test_mid_migration_crash_rollback`: Injects faults at discrete crash points, verifying WAL recovery or explicit rollback discards uncommitted changes, leaving DB at `user_version=3`:
  - *Point 1 (Backup fail/crash on R):* Explicit `ROLLBACK` on `M`, uncommitted state dropped, partial temp backup removed.
  - *Point 2 (Mid-DDL crash on M):* WAL recovery discards table rewrites; tables remain intact at schema version 3 (user_version = 3).
  - *Point 3 (Mid-rebuild crash on M):* WAL recovery discards partial projections; state intact at schema version 3 (user_version = 3).
  - *Point 4 (Integrity violation on M):* Failed `foreign_key_check` triggers explicit `ROLLBACK`.
  - *Point 5 (Pre-commit crash after user_version bump on M):* Crash before `COMMIT` discards version bump; reopens at `user_version=3`.
- `test_backup_restore_drill`: Validates full data restoration and verification from `.pre-v2.*.bak` after simulated fatal failure.
- `test_projections_rebuild_from_sources`: Truncating all derived projection tables and running `peerhub db rebuild-projections` regenerates exact state from underlying deliveries, evidence, session history, and observations.
