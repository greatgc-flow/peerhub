## 2. Operational/harness quirks observed (not design defects, but worth remembering)

- **Real Gemini backend capacity exhaustion, not a local dispatch bug (2026-08-21 ~03:50-04:11).** After roughly 40 consecutive successful ag dispatches in one long session, 6 consecutive `ag.deepthink`/`ag.effort` dispatches for Round 42 failed with a generic `nonzero_exit`, auto-triggering hub.py's peer-quarantine mechanism each time. Root-caused via a dedicated operational-diagnostic dispatch to cx (not a design review): cx inspected the real local `cli-*.log` files and found the actual captured backend errors were `503: No capacity available for model gemini-pro-agent` and `Error: Our servers are experiencing high traffic right now, please try again in a minute` — genuine, transient Gemini provider capacity exhaustion on the higher-tier models, not a stale lease, leaked handle, or broken dispatch mechanism (confirmed negative: all failed PIDs exited cleanly, leases terminated normally, no resource leak). cx also found and reported (but did not fix, out of scope for this dialectic) two real hub.py bugs worth a future P: exception request: (1) its failure classifier recognizes numeric `503` but not the plain-English capacity-exhaustion phrases actually returned, so these get mislabeled generic `nonzero_exit` and poison peer-wide health/trigger unnecessary quarantine; (2) on a PTY-branch nonzero exit it prints only `ag exited 1` to the terminal, discarding the actual captured error text that IS present in `error-log.jsonl`/`operational_errors.jsonl`, making this class of failure look uninformative when it isn't. **Resolution that worked**: `peer-recover` alone doesn't fix backend capacity (as cx correctly warned), but backing off ~60s and routing the same request to `ag.standard` (a lower, apparently less capacity-constrained tier) succeeded immediately. Splitting the original 3-item Round 42 into 3 smaller single-item dispatches was tried in parallel and may also have helped, though the capacity issue looks like the primary cause given a similarly-sized diagnostic ping also failed on the loaded tiers.

- **"Killed" background dispatches can still have written real, complete work** before the kill landed — confirmed multiple times this session (e.g. the item-5 batch-1 lease-fix dispatch, the batch-5 parity-ledger dispatch). Always `git status`/read the target file before assuming a killed dispatch produced nothing and redoing the work from scratch.
- **Oversized-ask detection** in `hub.py` counts every line starting with `-`, `*`, `+`, or a numbered list marker across the *entire* prompt text, not just an intentional "items" section — bulleted context sections count too. Write dispatch prompts in flowing prose when possible to avoid tripping this.
- Very large single-shot tasks (e.g. "produce all 90 parity ledger rows in one pass") are prone to the dispatch spending its whole budget writing non-converging helper scripts instead of the actual deliverable. Splitting into fixed, explicit batches (e.g. 18 actions at a time) worked reliably every time it was tried.
- ag will sometimes reconstruct content from a paraphrased summary instead of using verbatim source text if a fresh session is given only a summary — always paste full original text (or point at an already-committed file) rather than re-describing it from memory when asking for a faithful reproduction.

## 3. Real empirical findings worth keeping regardless of Phase 1's outcome

- **hub.py idempotency audit** (Round 5 item 5, all 90 actions): a large fraction of hub.py's actions were previously assumed idempotent in earlier drafts but are not — see the five `PHASE1-PARITY-LEDGER-BATCH*` documents for the full per-action verdict with line evidence. This is genuinely useful knowledge about the legacy system independent of whether Phase 1 proceeds, since any future caller of `hub.py` directly (not just peerhub) should know which actions are safe to retry blindly and which are not.
- **Real race condition found**: `thread-new` (and, per Round 5 item 5 batch 5, likely `proposal-add`, `thread-react`, `proposal-vote`, `lesson-sweep`, `thread-append` too) has an unlocked check-then-act pattern (`path.exists()` followed by an unlocked append) that can produce duplicate records under concurrent callers. This is a real bug in the *legacy* `hub.py`, independent of the peerhub migration — worth deciding separately whether to backport a fix to `hub.py` itself or just carry the correct locked behavior into peerhub's replacement.
- **Real ACL/transport findings** (Round 5 item 3): the originally-designed admission rule ("directory must deny unprivileged writes") would have rejected every real CLI installation on this machine, since `Authenticated Users:(M)` is the Windows default on portable/secondary NTFS volumes. The corrected rule (deny `Everyone`/`ANONYMOUS LOGON`/`Guests` write access specifically) is the one that's actually meaningful and achievable — this is a generally-applicable lesson for any future Windows-targeted admission/trust design, not just this project.

## Round 113 (item C, redesign review 6): relational schema confirmed converged; 3 filesystem-protocol issues remain, including a real security regression

cx's headline finding: **"the relational schema has converged."** The SQL block re-executed cleanly with no new defect across 6 consecutive fresh passes now — the schema/CHECK-constraint layer of the redesign is done. 3 filesystem-protocol issues remain:

1. **Security regression, introduced by Round 112 itself**: the prior explicit exclusive/no-follow staging-creation requirement was removed and replaced with "overwrite a mismatching pre-existing file in place." Combined with the new deterministic, fully-predictable staging/backup path names (from the same round's fix), this opens a real local attacker path: a symlink pre-placed at the deterministic path could be followed and its target corrupted; a hardlink pre-placed there could have its shared inode mutated by a truncate/metadata-apply.
