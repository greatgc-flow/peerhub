## MAJOR FINDING (2026-08-28): Tier 4 is NOT "entirely undesigned" -- a complete legacy behavior spec for all 90 actions already exists

While researching Tier 3's `thread-promote`, cx cited `docs/design/PHASE1-PARITY-LEDGER-BATCH1..5-2026-08-20.md` -- five docs, 18 entries each, **90 total, one per `LEGACY_CATALOG` action** (verified: `grep -c "^## [0-9]" docs/design/PHASE1-PARITY-LEDGER-BATCH*.md` gives exactly 18×5). Each entry is an exhaustive, line-number-precise specification of the REAL legacy `hub.py` behavior for that action: input schema, exact success/error output strings, before/after state changes with real file paths and JSON shapes, idempotency semantics, concurrency/crash behavior, and test fixtures. Spot-checked one entry (`thread-promote`, Batch 5 §7) directly against the real doc -- it precisely matches what cx cited, down to legacy source line numbers.

**This changes the whole backlog's risk/effort assessment.** What this doc's Tier 4 called "entirely undesigned domains" is actually "the legacy BEHAVIOR is completely and precisely specified; what's missing is the mapping from that spec into peerhub's native TargetState/service architecture" -- the same kind of work already done successfully for every domain built this session, not blank-slate design work. The `HUB-REPLACEMENT-GAP3-SESSION-CONTINUITY` doc's own narrative descriptions (used for `send`/`mark-read`/`thread-promote`'s command-table entries) turn out to have been written WITHOUT consulting this parity ledger, and at least one of them (`thread-promote`) was factually wrong as a result -- see the ratification below.

**Action for whoever picks up any Tier 3 or Tier 4 item next: read the matching Parity Ledger entry FIRST**, before assuming a design round is needed from scratch. Many "undesigned" Tier 4 items may turn out to need only the same "map real legacy behavior to a TargetState/service shape" exercise already proven this session, not a genuine open design question. This doesn't mean zero design work remains (peerhub's native shape for a given legacy behavior is still a real choice, as `send`'s ratification below shows), but the *behavioral* ambiguity that made Tier 4 look intimidating is mostly illusory -- it was never actually undocumented, just unread.

## Tier 3 RATIFIED (2026-08-28): all 7 items resolved via one cc/cx research-then-critique round

cx researched all 7 against real Parity Ledger entries + real service code (not speculation); the terminal independently verified the single most surprising claim (`thread-promote`) directly against the source doc and confirmed it precisely. No disagreement found this round -- cx's research was thorough enough that the terminal's role was verification, not correction.

1. **`send`** — RATIFIED: a new `inbox-message:<id>` `TargetState` family (NOT a reuse of `RoomsService.append_message()`, which would force every private notification into public thread history -- exactly what gap-3's "transient... doesn't duplicate substantive thread content" language was trying to avoid). Real legacy behavior (Parity Ledger Batch 1 §3-5) uses `mailbox.json` + a per-recipient maildir -- durable, not literally ephemeral, "transient" means "not substantive thread content," not "non-persisted." Shape: `sender`, `recipient` (composite instance+profile identity), `body`, optional `thread_ref`/`resource_ref`, `correlation_id`. **Real open flag, ratified as a requirement, not deferred**: the generic broker has no per-target read authorization -- whoever implements `message.check` (item 5 below) MUST add an explicit sender-or-recipient check at the command-descriptor/handler level (the broker itself won't do it), or this "private" message isn't actually private.
2. **`mark-read`** — RATIFIED: cursor identity `inbox-cursor:<room_id>:<recipient_instance_id>:<recipient_profile_id>`, tracking a per-recipient monotonic mailbox sequence (needs its own allocator, since UUIDs/timestamps aren't reliable order) -- NOT thread-message read state, confirmed via the real native name `inbox.cursor.advance` in the gap-3 doc's own command table. **Ratified scope decision**: v1 implements a pure high-water-mark cursor ("everything through sequence N is read"), NOT legacy's exact per-message out-of-order mark-as-read capability -- a conscious, documented simplification (matching the "superset-compat, never silently narrow" principle used elsewhere this session would actually argue AGAINST this simplification if taken literally, but per the "don't design speculatively" principle also used this session, add sparse per-message acknowledgements only if real evidence shows out-of-order reads are actually needed, not up front).
3. **`thread-promote`** — RATIFIED, and this is a real correction to the earlier gap-3 doc's own text: legacy `thread-promote` does NOT "attach a thread to a request/proposal/consensus round" (that was the gap-3 doc's own narrative guess, written without the parity ledger). Real legacy behavior (Parity Ledger Batch 5 §7, independently verified against the source doc): promotes ONE MAILBOX MESSAGE (`msg_id`) into a target thread as a `MSG_PROMOTED` entry, marking the source message `promoted_to`. **Split into two, ratified separately**: (a) legacy `thread-promote` belongs with the `send`/mailbox build (items 1/2/5) -- a promoted message becomes a new thread message whose metadata carries `promoted_from_inbox_message_id`; (b) the gap-3 doc's ORIGINAL "attach thread to governance object" idea is a genuinely different, NEW concept with no legacy equivalent at all -- explicitly moved OUT of Tier 3 entirely (not even ratified as Tier 4-ready) because it has a real prerequisite gap: `ConsensusService.propose()` currently creates rounds with `scope: None`, so same-room validation for a thread-to-round link isn't even possible yet. `promoted_from_thread_id` (the field already in the early gap-3 schema draft, absent from the final concrete schema and from the real `create_thread()`) is reserved for thread-to-thread lineage only, per the evidence -- not either of the above concepts.
4. **`update-status`** — RATIFIED: moved to Tier 4. Confirmed via direct repo grep: no "mission" concept exists anywhere in real peerhub code. `room-goal` is NOT a sufficient hook (no `blocked`/`phase` modeling, no lifecycle/authority semantics). Real legacy behavior (Parity Ledger Batch 1 §8) atomically updates `mission`/`blocked`/`phase` on `state.json` -- fully spec'd behaviorally, but genuinely needs a room-schema extension (new fields + their own CAS/authority rules) before it's a quick wiring task, unlike most of this batch.
5. **`check`** — RATIFIED: the read side of `send`'s mailbox (Parity Ledger Batch 1 §9: reads/formats unread mailbox messages, no mutation, no implicit cursor advance, doesn't touch threads). Build together with items 1/2/3(a).
6. **`arbiter-review`** — RATIFIED: stays Tier 3-adjacent but is explicitly NOT a quick wiring task like the rest of this batch. Confirmed neither `ConsensusService.resolve()` nor `request_escalation()` invoke a real arbiter or record an opinion -- real legacy behavior (Parity Ledger Batch 5 §16) evaluates trigger/dissent/budget rules, **invokes the configured arbiter in an isolated subprocess**, and records a final opinion. That subprocess-invocation capability doesn't exist anywhere in peerhub yet (it's a different kind of infrastructure than anything built this session, closer in kind to the `ProcessSupervisor`/peer-dispatch machinery than to a simple CAS-governed service method). Mechanics are drafted (immutable `arbiter-review:<round_id>:<review_id>` request + `arbiter-opinion:<round_id>:<review_id>` result + a new authority-validating consensus transition, consistent with `ARCHITECTURE.md`'s already-ratified "consensus produces intent, application dispatches, consensus records the opinion" split) but this item needs its own dedicated implementation round, not a same-batch wiring pass with the mailbox items.
7. **`lesson-broadcast`** — RATIFIED and now DONE (35 of the 90 `LEGACY_CATALOG` actions backed, up from 34). `RoomsService.list_participants()` added; new `peerhub/application/lesson_broadcast.py` orchestrates: validates the lesson is ACTIVE, excludes the sender from the room's real participant list, creates a `lesson-broadcast:<id>` campaign record, delivers a real mailbox message via `send_message()` to each recipient AND records `record_delivery_pending()` for each -- IMMEDIATE per-recipient delivery, matching real legacy behavior, per this session's "never silently narrow legacy behavior" principle. `LessonService` confirmed to have zero new dependency on room storage (`peerhub/governance/lessons.py`'s imports checked directly -- no `rooms` import). **Resolved a real tension**: this session's earlier lesson-domain ratification (item 37, "pack invalidation + next-dispatch eligibility is the baseline, immediate notification is only an optimization") describes a DIFFERENT mechanism -- how lessons passively surface in an already-active session's context -- not what the explicit `lesson-broadcast` COMMAND does; the two coexist rather than one redefining the other. Independently re-verified by the terminal through the real CLI: broadcasting excludes a sender whose identity matches a real room participant (delivers to the other 2, not 3), and broadcasting an unactivated (`PROPOSED`) lesson is correctly rejected (exit 2, clear message) rather than silently succeeding.

**Net effect on the backlog, updated as items closed**: items 1, 2, 3(a), 5, and 7 are all DONE (`send`/`check`/`mark-read`/promote-from-mailbox/`lesson-broadcast` -- see the update notes below each). Item 4 (`update-status`) moved to Tier 4 (needs a room-schema extension first). **Item 6 (`arbiter-review`) is the only Tier 3 item left** -- needs its own dedicated round, new subprocess-invocation infrastructure, not just a wiring task.

**Update (2026-08-28, mailbox wiring round): CLI + legacy + dispatcher wiring DONE too -- 34 of the 90 now backed** (up from 30). `send`/`check`/`mark-read`/`thread-promote` all now translate and execute end-to-end (`peerhub room send|check-inbox|mark-read|promote-message`, `LegacyTranslator`, `ApplicationAPI`). `coordination.message.check`'s read-only descriptor wraps its `Sequence[TargetState]` result as `{"messages": [...]}`, reusing the exact fix pattern already established for `lessons-list` (never return a bare list from an `encode_result_fn`). Independently re-verified by the terminal through the FULL CLI stack (not just cx's own in-memory smoke): sent 2 private messages to different recipients in the same room, confirmed each recipient's `check-inbox` shows only their own mail and the sender's own inbox is empty. pytest -q: 1136 passed (only the known pre-existing failure). pyright: 0 new errors.

**Update (2026-08-28, mailbox core round): DONE (service layer only).** `RoomsService` (peerhub/governance/rooms.py) gained `send_message()`, `check_inbox()`, `mark_read()`, `promote_message()` -- immutable `inbox-message:<id>` targets, CAS-updated `inbox-cursor:<room>:<recipient>` projections, sequence allocation mirroring the existing thread-message pattern. The non-negotiable privacy requirement is enforced by construction: `check_inbox` only ever queries the CALLER's own inbox (scoped by `recipient` match), never another identity's. Independently re-verified by the terminal with a fresh, separately-written smoke script (not just re-running cx's own tests) proving 3-way privacy isolation (2 recipients each see only their own message, a 3rd bystander sees nothing) -- this was extra-important this round since cx's sandbox couldn't run pytest OR a real SQLite smoke test at all, only an in-memory check. `mark_read` is idempotent (repeat calls to an already-passed sequence leave the cursor's stored state unchanged). `promote_message` creates a real `MSG_PROMOTED` thread message carrying `promoted_from_inbox_message_id` and marks the source inbox-message's `promoted_to` field via CAS (revision bumps, body/sender/recipient stay immutable). CLI + legacy-translation + execution-dispatcher wiring is an explicit follow-up round (matching how every other domain this session was built: core first, wiring later) -- doesn't move the `LEGACY_CATALOG` backed-action count yet.

Resolve "does peerhub own this or does it stay host-side" before designing, not after.
- **Alert** (1 action): `alert-raise` — standalone, undesigned.
