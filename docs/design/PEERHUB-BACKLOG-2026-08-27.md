
#### `report-error` Auto-quarantine Gap Assessment (2026-08-31)

**RESEARCH FINDINGS:**
1. **`HealthService.classify_and_open_circuit()` requirements:** Direct inspection (`peerhub/health/service.py:1057-1072`) confirms this method strictly requires typed evidence (`attempted_trace: tuple[HealthStageObservation, ...] | list[HealthStageObservation]`) and an optional `evidence_subject: EvidenceSubject | None` and `receipt: PolicyReceipt | None`. There is genuinely no legitimate way to construct these types from a free-form `report-error` string (peer_key, pattern, severity, detail, actor_id, count). Doing so would fabricate evidence, repeating the exact authority-model mistake rejected for `peer-quarantine`.
2. **Legacy `report-error` auto-quarantine behavior:** Legacy (`P:/_sys/core/hub.py:9532-9533`) blindly checks if the threshold is crossed and directly calls `action_peer_quarantine(ai_root, event["peer"], f"operational_error:{event['pattern']}")`. It uses the exact same `peer-quarantine` false-friend machinery which bypasses proper evidence/authority models.
3. **The honest boundary:** The `OperationalErrorService`'s current behavior of creating a distinct immutable `quarantine-review` target (`peerhub/governance/operational_errors.py:224-249`) already represents the CORRECT honest boundary. A full search of the `peerhub` directory confirms that **nothing consumes `quarantine-review` targets today**. The real gap is not inside `report-error`, but the lack of a review-consumer (a coordinator that reads these targets and routes them to an authority-bearing process like `authorize_administrative_recovery()`).

**VERDICT:**
There is no legitimate honest mapping from a free-form string to typed evidence without inventing evidence. Therefore, **`report-error`'s auto-quarantine must stay permanently deferred** as originally decided. The review-request creation already implemented is the correct and complete native equivalent. The remaining work belongs to a separate, future review-consumer domain, not `report-error`.

### `LeadershipService` RATIFIED (2026-08-30): a real workspace-global singleton, deliberately NOT built on DutyLeaseCoordinator

Research (cx.deepthink) then critique (cc.deepthink), both independently spot-checked by the terminal directly against real `_sys/core/hub.py` source -- every checked claim, including two genuinely counterintuitive ones, confirmed accurate: **an unexpired `challenge_until` window PERMITS a competing claim to overwrite the pending claimant -- it does NOT protect the incumbent** (health-gating only protects a leader once the window has expired or never existed; the opposite of the natural-sounding assumption); and **`DutyLeaseCoordinator`'s existing AP-20-style guard has a genuine off-by-one vs. real legacy** (rejects the 3rd same-peer claim; legacy allows claims 1-3 and rejects the 4th) -- separate confirming evidence, not a bug to fix in `duty_lease.py` itself, that `LeadershipService` must not reuse that machinery.

**Placement: `peerhub/application/leadership.py`, NOT built on `DutyLeaseCoordinator` at all.** Confirmed incompatible on every axis: room-scoped vs. legacy's workspace-global; immediately-`ACTIVE` vs. legacy's `PENDING`-with-challenge-window; heartbeat-expiring vs. legacy's non-expiring; fence-strict-yield-rejection vs. legacy's warn-and-vacate-for-anyone. The currently-shipped `routing.leadership.claim`/`.yield` (the bug this replaces) are exactly this wrong reuse.

**Schema: one singleton `leadership:workspace` target** (matching `arbiter-budget:workspace`'s precedent for when a singleton is justified -- a genuine workspace-wide at-most-one-leader invariant, and AP-20's check-then-append must be atomic with the leadership write in one `broker.submit()`). State: `status` (`VACANT|PENDING|ACTIVE` -- `ACTIVE` is reserved vocabulary this round, nothing in this round's scope ever writes it, see below), `term` (native-only audit convenience, explicitly non-authoritative, nothing may gate on it), `claim_id` (fresh every successful claim), `leader` (null, or `{peer_node_id, peer_node_target_id, peer_node_revision, peer_kind, profile_id, adapter_version}` -- a frozen registry binding, requiring `peer_registry.get_node()` to resolve; unregistered-text leaders are rejected, closing a real legacy pathology where an unresolvable agent name becomes permanently unchallengeable since it always reads as health `UNKNOWN`), `claimed_at`, `claimed_by`, `challenge_until`, `domain`, `reason` (both with legacy's exact fallbacks: `domain = domain or reason or "general"`, `reason = reason or "manual_claim"`), `claim_basis` (null, or `{disposition: VACANT_CLAIM|SELF_RECLAIM|OPEN_WINDOW_CHALLENGE|FAILED_INCUMBENT_TAKEOVER, incumbent_peer_node_id, projection_id, projection_revision, availability_state, admission_state, stale_at_read}`), `yielded_by`, `yielded_at`, `yield_reason`, `coordinator_history` (embedded, bounded to last 10, matching legacy's own `history[-10:]`), `updated_at`.

**Claim predicate** (re-evaluated fresh on every CAS retry): AP-20 first, unconditionally (applies even to a self-reclaim, matching source ordering) -- reject iff the last `threshold` history entries all belong to the candidate. Then: `VACANT`/absent -> `VACANT_CLAIM`; candidate equals current leader -> `SELF_RECLAIM`, no incumbent health check; `challenge_until is not None and now < challenge_until` (gated purely on the timestamp, no `status` condition -- a narrowing cx's draft had that critique removed) -> `OPEN_WINDOW_CHALLENGE`, unconditional; otherwise evaluate the *incumbent's* health via `HealthService.get_health_projection()` on its stored `peer_kind`/`profile_id` -- replaceable (`FAILED_INCUMBENT_TAKEOVER`) only if a projection exists AND (availability in `{UNAVAILABLE,STALE}` OR admission in `{QUARANTINED,COOLDOWN,RECOVERY_REQUIRED}` OR stale past `readiness_freshness_seconds`); otherwise raise `LeadershipIncumbentProtectedError` -- absent evidence protects the incumbent (the mirror image of role-assignment's fail-open-admits-a-candidate polarity: same deny-list shape, opposite user-visible outcome, since this gates an incumbent rather than admitting a candidate). The new candidate itself is never health-gated -- legacy only ever gates the incumbent.

**Yield**: always mutates (even already-`VACANT`, no target, or a non-leader yielding -- returns `owner_mismatch`/`previous_leader_peer_node_id` as warning metadata, never raises). Legacy fully *replaces* the `leadership` sub-object rather than partially updating it, so yield must null `leader`/`claim_id`/`challenge_until`/`claimed_at`/`claimed_by`/`domain`/`claim_basis`, not just set `status=VACANT` -- retaining a stale `challenge_until` after a yield (cx's original draft) would leave actively misleading residue. `term` and `coordinator_history` are retained (legacy siblings of `leadership` in `state.json`, untouched by yield).

**No `activate_pending_leadership()` this round** -- decisive new evidence found in critique: grepping every real legacy write of `leadership.status = "ACTIVE"` found exactly one call site, and it belongs to `action_terminal_handoff`, a *different* action in a domain peerhub already has (`TerminalDutyService`) -- not a timeout-driven settle step. Nothing in legacy ever transitions `PENDING` to `ACTIVE` on elapsed time; there is no legacy sweep/settle/activate operation at all. Building one now would be an invented state transition with no legacy counterpart and no caller. The `ACTIVE` <- `terminal-handoff` cross-domain coupling is recorded as a real, separate scoping question for later, not designed now.

**Retry**: bounded 16-attempt CAS loop (mirroring `ArbiterBudgetManager`), full predicate re-evaluated fresh each attempt -- justified because legacy serializes these operations under one real global lock, making CAS-retry-with-fresh-reevaluation the correct analog of sequential processing (a second concurrent claim genuinely should see the first's new `PENDING` state and be able to challenge it within the window), not a shortcut. Only `StaleRevisionError` may consume a retry attempt -- AP-20 and incumbent-protection rejections raise immediately, so a losing claimant doesn't burn 16 attempts re-deriving the same refusal. ### `report-error` RATIFIED (2026-08-29): two-round design, an immutable review-request bridge, not a forced circuit-open

Research-only pass (cc.deepthink) on the process-lease domain named as blocker (4) of `status` above, and on the previously-rejected `lease-status`/`lease-sweep` legacy actions. Every legacy claim below was re-derived directly from `P:/_sys/core/hub.py`, and every PeerHub claim from the shipped 49/90 tree. **Verdict: (a) -- a genuine new coordinator is needed -- but with two material scope corrections cx's pass did not have, one of which shrinks the reaping half substantially and one of which shows the health half is not actually unblocked.**

**Legacy contract, verified.** A "process lease" is one *dispatch attempt's* child OS process, not a peer's long-lived process. `_lease_open(ai_root, peer_id, pid, lease_timeout_sec, ask_id, ask_query_file)` writes one entry per ask into `ai_root/leases.json`, keyed by a fresh `uuid4` -- explicitly *not* by `peer_id` (an old bug where concurrent same-peer asks clobbered each other) and *not* by `ask_id` (`_short_id()` is only 4 hex chars, a real collision risk) (`P:/_sys/core/hub.py:10829-10860`). The entry is `{ask_id, peer_id, pid, room_id, started_at, expires_at, heartbeat_at, status, ask_query_file}` with `status="open"`. `peer_id` is the **fully-resolved dispatch target** (`ag.deepthink`), not a root peer. `_lease_renew` and `_lease_close` are keyed by `lease_id` and PID-checked, raising `LeaseOwnershipError` on mismatch rather than silently no-opping (`P:/_sys/core/hub.py:10862-10897`). Lifetimes come from `communication_policy` via `_lease_cfg()`: `lease_timeout_sec` (default 300, the orphan-cleanup window) is deliberately distinct from `zombie_timeout_sec` (default 600, profile-overridable, the in-flight silent-process kill threshold used by the ask heartbeat loop at `P:/_sys/core/hub.py:4579`, `P:/_sys/core/hub.py:4734`) -- `lease-sweep` is the *orphan* path, not the zombie path (`P:/_sys/core/hub.py:10773-10792`).

Liveness is a bare `os.kill(pid, 0)` (`_pid_alive`, `P:/_sys/core/hub.py:8098-8104`), wrapped by `_validated_live_lease_pid` which additionally rejects non-`int`/non-positive PIDs (`P:/_sys/core/hub.py:10822-10827`). **There is no PID-reuse protection at all** -- legacy will happily `kill` whatever process now holds a recycled PID. `_lease_sweep(ai_root)` (`P:/_sys/core/hub.py:10953-11053`) scans every `status == "open"` entry under the `leases` filelock: an unparseable `expires_at` becomes `status="invalid_timestamp"` with `quarantined=True`/`quarantine_reason`/`quarantined_at`; a past `expires_at` becomes `status="expired"`. Entries are **marked, never deleted**, so the sweep is convergent and a second run is a pure no-op. All slow/lock-taking work runs *after* the lease lock is released. For each expired entry it then (i) `_kill_process_tree(pid)` if the PID validates live, else prints `[HUB:WARN] expired lease {id} has invalid pid=...; kill skipped`; (ii) `_record_ask_failure(root_peer_id, "lease_expired", ...)` with `profile_key` split off a composite id; (iii) `_append_ask_history(..., "lease_expired")`; (iv) `_log_p2p("SWEEP", ...)`. `_kill_process_tree` is psutil `children(recursive=True)` + parent kill, falling back to `taskkill /F /T` on Windows or a bare `SIGKILL` on POSIX (`P:/_sys/core/hub.py:10920-10949`). `action_lease_status` is a pure read: `[HUB] No leases.json found.` / `[HUB] No active leases.` / else a fixed-width `Peer/Status/PID/Alive/Expires/Heartbeat` table with a 78-char divider, a live `psutil.pid_exists` probe rendering `YES`/`NO`/`ERR`, and a ` !` or ` !INVALID_TIMESTAMP` suffix on the status column (`P:/_sys/core/hub.py:11713-11746`). Both match the parity ledger (`docs/design/PHASE1-PARITY-LEDGER-BATCH4-2026-08-20.md:136-172`); `lease-sweep` is a zero-token `_SYSTEM_EXEMPT_ACTIONS` watchdog (`P:/_sys/core/hub.py:9169`) and is invoked implicitly by `init-session`, `status`, and every `ask` (`P:/_sys/core/hub.py:1369`, `P:/_sys/core/hub.py:1681`, `P:/_sys/core/hub.py:6528`), which is why `status` inherits the mutation cx flagged.

**CORRECTION 1 (load-bearing): `_lease_sweep`'s own docstring "Updates health to STALE" (`P:/_sys/core/hub.py:10954`) is FALSE, and the ledger's "updates peer health/history" understates it in a way that would produce a wrong port.** `lease_expired` is a member of `_TRANSIENT_REASONS` (`P:/_sys/core/hub.py:1792`). Tracing `_record_ask_failure`: transient reasons increment `transient_failures` and *reset* `consecutive_failures` rather than incrementing it; `critical_reasons.difference_update(_TRANSIENT_REASONS)` and the `not is_transient` guards mean `context_health.status` can never be set to RED or YELLOW by a lease expiry; and because `_lease_sweep` passes a non-`None` `profile_key` for composite targets, `is_profile_scoped` is True and every write lands in `availability.profiles["deepthink"]`, not on the root peer. The one real effect is `close_target_gate = True` (transient and not `terminal_timeout`), which sets **`gate_open = False`** on that profile and synthesizes a `rate_limit_state` exponential backoff of `min(300, 2 ** transient_failures)` seconds. So legacy's actual health semantics are: *an expired process lease closes one profile's admission gate for a short, self-clearing backoff window*. It does not mark anything STALE, does not degrade the root peer, and cannot quarantine. Any PeerHub port that renders this as a health-status downgrade is wrong.

**CORRECTION 2 (new, and it shrinks the reaping half): on Windows, PeerHub-spawned trees are bound with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, so the orphan class legacy reaps largely cannot arise.** `TreeController.bind_spawn` creates a Job Object and sets `LimitFlags = 0x2000` explicitly so "children die automatically if the parent process abruptly exits" (`peerhub/dispatch/tree_controller.py:212-241`). Legacy's `_lease_sweep` reaper exists because a `hub.py` invocation that died mid-ask left an orphaned `agy`/`node` subprocess with nothing to kill it. In PeerHub that subprocess is already dead when the owning process's handle closes. The residual reapable population is narrow and explicitly documented: children spawned by the root *before* `AssignProcessToJobObject` can escape containment, and "RECONCILE_TREE re-observation is the accepted safety net for an escaped child, not a guarantee of prevention" (`peerhub/dispatch/tree_controller.py:20-24`), plus anything not spawned through `bind_spawn` at all. This does not delete the domain -- the *lease-state* recovery and health/history halves are untouched by it -- but it means a PeerHub sweep's reaper is a residual-cleanup safety net, not the primary mechanism it is in legacy, and the design should say so rather than porting the reaper at legacy's weight.

**CORRECTION 3 (new): the kill primitive cannot be driven cross-process, because `TreeHandle` is not persistable.** cx's framing that PeerHub has "an identity-verifying `TreeController.kill_tree()` OS primitive" but no composing coordinator is confirmed exactly -- `verify_process_identity` (`peerhub/dispatch/tree_controller.py:152-175`) has **four call sites, all inside `tree_controller.py` itself** (`:271`, `:328`, `:375`, `:456`) and no external caller anywhere in the tree. But the sharper constraint is what `kill_tree` needs. It takes a `TreeHandle`, and the concrete `ProcessTreeHandle` carries a live `subprocess.Popen` and a raw Windows Job Object `HANDLE` int (`peerhub/dispatch/tree_controller.py:41-48`) -- neither survives the creating process. What *is* persisted is only `owner_process_pid` + `owner_process_creation_time` (`peerhub/persistence/migrations/0003_command_request_attempt.sql:101-102`, rehydrated into a `ProcessBirthIdentity` at `peerhub/persistence/sqlite_dispatch.py:1254-1261`). A fresh `peerhub lease-sweep` process can therefore reconstruct the *identity* and call `verify_process_identity` (both args are plain ints -- this is genuinely reusable), but a `TreeHandle` rebuilt from it has `win_job_handle is None`, and `kill_tree` then falls through to an identity-verified `TerminateProcess` on the **root PID only** (`peerhub/dispatch/tree_controller.py:398-415`) -- a single-process kill, not a tree reap. POSIX degrades the same way to `pgid = ... or root.pid`. So "reuse the existing kill primitive" is only half-true: the identity check ports cleanly, the tree reap does not.

**What PeerHub already has, precisely.** The persisted `leases` table is structurally *stronger* than legacy's `leases.json`: `lease_id`, `session_id`, `command_id`, `attempt_id`, `fencing_token`, `authority_epoch`, `revision`, `owner_principal_id`, `owner_instance_id`, `owner_peer_id`, the dual-key process birth identity, a 10-value `state` enum, and `heartbeat_expires_at` (`peerhub/persistence/migrations/0003_command_request_attempt.sql:91-135`). `expire_and_recover_lease` is a complete pure reducer that already distinguishes `ABANDONED_PRE_SPAWN` / `IDENTITY_MISMATCH` / `FENCED` and emits a `RecoveryReceipt` (`peerhub/dispatch/model.py:1220-1275`), and `SessionLeaseService.recover_lease` commits it under CAS with the receipt in one unit of work (`peerhub/dispatch/session_lease.py:278-330`). The dedicated heartbeat worker already refuses ghost renewals by checking `process.poll()` and the recorded identity (`peerhub/dispatch/heartbeat.py:1-19`). Four things are missing, and only four:

1. **No enumeration.** There are exactly two `FROM leases` queries in the whole persistence layer: `get_lease(lease_id)` (`peerhub/persistence/sqlite_dispatch.py:1240-1246`) and `count_active_leases` (`peerhub/persistence/sqlite_dispatch.py:1337-1352`). There is no expired-lease scan -- contrast `list_expired_duty_leases`, which exists for duty leases (`peerhub/persistence/sqlite_dispatch.py:295-305`). A sweep needs a **new persistence read**, not just a new coordinator.
2. **No observation producer.** `recover_lease` requires the caller to supply `is_process_alive` and `process_identity_matches` already-observed (`peerhub/dispatch/session_lease.py:286-287`), and nothing in the tree produces them for a persisted lease.
3. **No reaping composition**, subject to Correction 3.
4. **No health/history fan-out.** `count_active_leases` is consumed only as a scalar by the CLI dashboard (`peerhub/cli.py:2638`); `recover_lease` reaches the public service surface (`peerhub/dispatch/service.py:1006-1019`) but has **no non-test caller**. *Placement*: `peerhub/application/process_lease_sweep.py`, `ProcessLeaseSweepCoordinator`. Application layer, not `governance/`, because it composes three distinct owners -- `SessionLeaseService` (dispatch state), `TreeController` (OS), and health/history -- which is the same cross-domain rationale that places `AlertRaiseCoordinator` and `LeadershipService` there, and the opposite of the self-contained test that put `FileLockService`/`FeedbackService` in `governance/`.

*New persistence read* (mirroring the duty-lease precedent at `peerhub/persistence/sqlite_dispatch.py:295-305`): `list_expired_leases(as_of: int, *, limit: int = 100) -> Sequence[LeaseSnapshot]`, `WHERE state IN ('RESERVED','ACTIVE','RENEWED') AND heartbeat_expires_at < :as_of ORDER BY heartbeat_expires_at, lease_id`, added to the dispatch read unit of work and `StateStore`.

*Constructor*: `ProcessLeaseSweepCoordinator(sessions: SessionLeaseService, *, store, tree_controller, clock, ids, policy_id, policy_revision)`.

*Methods*:
- `sweep(*, recovery_actor_principal_id: str, as_of: int | None = None, limit: int = 100, reap: bool = True) -> ProcessLeaseSweepReport`. Per expired lease: rehydrate `ProcessBirthIdentity`; call `verify_process_identity(identity.pid, identity)` to derive `process_identity_matches`, and `is_process_alive` from the same probe; call `sessions.recover_lease(lease_id, trigger=RecoveryTrigger.HEARTBEAT_TIMEOUT, is_process_alive=..., process_identity_matches=..., ...)`, letting the existing reducer pick `FENCED` / `IDENTITY_MISMATCH` / `ABANDONED_PRE_SPAWN`; then, only when `reap` and the identity verified and the process is alive, terminate. Convergent and idempotent by construction: `recover_lease` moves the lease out of the swept state set, so a second run finds nothing -- matching legacy's mark-never-delete behaviour without needing legacy's `changed` flag.
- `status(*, as_of: int | None = None) -> Sequence[ProcessLeaseObservation]` for `lease-status`: one row per non-terminal lease carrying `owner_peer_id`, `state`, `pid`, an `alive` tri-state (`YES`/`NO`/`ERR`, from the same identity probe), `heartbeat_expires_at`, and an `expired` flag. Structured return, rendered by the CLI -- the same collect-then-render split cx recommends for `StatusCoordinator`.

*Reaping, stated honestly*: v1 should add `TreeController.kill_by_identity(identity: ProcessBirthIdentity) -> TreeDispatchReceipt` -- identity-verified single-process termination reusing `verify_process_identity` -- and **must not** be documented as a tree reap. Persisting a re-bindable tree token is the only route to real cross-process tree termination and should be deferred to its own round, with the residual gap recorded rather than papered over.

CHECK (heartbeat_expires_at >= 0)` (`peerhub/persistence/migrations/0003_command_request_attempt.sql:118-119`), so the entire quarantine branch and its `fix-lease-sweep-inv-01` fixture are structurally unreachable -- a deviation, not a bug. **Update (2026-08-31): Re-assessment of health fan-out gap.** Research confirms this gap remains **genuinely blocked**. The health infrastructure built tonight (`RecoveryProbeGrant` lifecycle, `HealthService.authorize_administrative_recovery`, etc., in `peerhub/health/contract.py` and `peerhub/health/service.py`) provides the pipeline to recover *from* a bad state (`QUARANTINED` / `COOLDOWN` to `OPEN`). However, it does NOT provide the mechanism needed to *put* a profile into a transient bad state with a backoff in the first place. The only existing writer is `HealthService.classify_and_open_circuit` (`peerhub/health/service.py:1057`), which requires a synchronous `attempted_trace` of `HealthStageObservation` (for inline execution failures like `RESOLVE_EXECUTABLE`, `peerhub/health/contract.py:124`), and applies a full circuit trip (`CircuitState.CIRCUIT_OPEN`, `peerhub/health/model.py:472`). This is a fundamentally different mechanism from `process-lease-sweep`'s requirement: a background watchdog that closes a profile's admission gate for a self-clearing backoff without generating a circuit trip or requiring an RPC failure trace. The original finding stands: a distinct writer for transient profile backoffs is still needed.

#### Transient Profile Gate Backoff: Design Sketch and Sizing (2026-08-31)

**RESEARCH FINDINGS:**
1. **Existing Admission States:** Direct inspection of `peerhub/health/contract.py:85-92` confirms the enum contains `OPEN`, `COOLDOWN`, `RECOVERY_REQUIRED`, `QUARANTINED`, `PROBE_AUTHORIZED`.

The health model is built on strict monotonic worst-of precedence rules and a non-negotiable "no direct healthy write" contract. Introducing a state that *does* self-clear to healthy (even if it's modeled as a separate parallel gate rather than an `AdmissionState`) touches the exact load-bearing assumptions that required multiple rounds for manual-quarantine. #### Critique (ag.deepthink, second pass, 2026-08-31)

1. **AdmissionState.COOLDOWN transitions:** CONFIRMED. peerhub/health/model.py:248-251 proves that when COOLDOWN expires, it dynamically degrades to RECOVERY_REQUIRED rather than self-clearing. The assessment that a new path is needed is correct.
2. **Composition with QUARANTINED:** REFUTED (GAP). The proposal states "the gate is treated as closed" but fails to specify how this composes with a concurrent QUARANTINED state. A profile could legitimately be quarantined while under a transient backoff. The proposal misses the resolution logic: does one override the other? If so, what is the effective state? The proposal is dangerously vague on this composition.
3. **Safety principle violation (self-clearing without evidence):** CONFIRMED (Legitimate exception). RUNTIME-HEALTH-DRIFT-2026-07-28.md forbids granting HEALTHY without new evidence. However, transient backoff simply suppresses the *underlying baseline* state. When the backoff expires, it doesn't mint a new readiness receipt; it just unmasks the baseline projection (which is still subject to staleness checks and existing circuits). It is not asserting *new* health, just lifting a temporary restriction, which is safe.
4. **Data placement (HealthProjectionSnapshot vs separate entity):** REFUTED. Adding this directly to HealthProjectionSnapshot (as the primary suggestion) is a mistake. 5. **Sizing Verdict:** REFUTED (Oversized). The verdict claims "Modifying the core health projection pipeline... is high-risk." ### `status` blocker re-assessment after the landed health-authority bridge (2026-09-01): two support gaps are now small, but the room SSOT and process sweep remain separate work

Research-only pass against the real legacy handler and the shipped 50/90 tree. **Overall verdict: the landed health-authority bridge does not make full `status` parity implementation-ready.** It does sharpen the split: the unread aggregate and request-context room resolution are small, tractable read/boundary additions; the authoritative room summary is still unbuilt; and process-lease reconciliation still needs its own persistence/OS coordinator plus a different transient-backoff health writer. The bridge that landed is specifically a single-use recovery-probe grant and administrative recovery path (`peerhub/health/contract.py:773-868`, `peerhub/health/service.py:1318-1471`), not a general authority to write dashboard state or process-failure backoffs.

It is therefore a last-change timestamp for the legacy shared room/workspace state object, not a timestamp that can honestly be reconstructed from mission alone.

`RoomsService` has related fragments under other names, but no equivalent owner. A room record exposes `topic_id`, `title`, fixed `status="active"`, and message/session projections, with no mission, blocked, or phase field (`peerhub/governance/rooms.py:63-102`); `clear_room()` merely creates a fresh room with the subject copied into topic/title (`peerhub/governance/rooms.py:139-160`). Taking room title/goal + alert.blocked + room.status + `max(updated_at)` would invent a composite semantic and still lose valid legacy writes. `coordination.mission.update` remains only a catalog mapping and falls through to the generic unbacked result (`peerhub/application/legacy.py:129-140`, `peerhub/application/legacy.py:1823-1830`). **Verdict:** surrounding pieces make the eventual writer easier to compose, but an authoritative room-summary target (or an explicit extension/migration of `room-goal`) and its update/lifecycle/alert write rules still need their own design.

**2. Aggregate unread mailbox count -- NOW SMALLER/TRACTABLE, but a new scalar read and scope rule are still required.** Legacy `status` does not calculate a caller inbox: it reads the cached workspace-global `mailbox.json.unread_count` without a recipient filter (`P:/_sys/core/hub.py:1680-1704`). That cache counts message records whose status is `unread`; send creates one unread record per concrete destination and recomputes the total, broadcast calls send once per target, and mark-read recomputes after changing only the named target's messages (`P:/_sys/core/hub.py:1459-1522`, `P:/_sys/core/hub.py:1530-1569`, `P:/_sys/core/hub.py:1572-1583`). Mailbox records have no room key. `new-topic` leaves this mailbox intact, whereas `clear-room` resets the whole cache to zero (`P:/_sys/core/hub.py:3540-3573`, `P:/_sys/core/hub.py:3576-3586`), so strict parity is workspace-global-since-last-clear, not simply "current room."

The native storage mechanics are already sufficient for a straightforward, deterministic unread-delivery count: every `inbox-message` is room-scoped, addressed to one `(instance_id, profile_id)`, and gets a sequence allocated within that recipient/room stream (`peerhub/governance/rooms.py:210-300`); every recipient has a room-scoped high-water cursor (`peerhub/governance/rooms.py:344-417`); and `check_inbox()` already defines unread as a matching recipient delivery whose sequence exceeds that cursor (`peerhub/governance/rooms.py:302-342`). A contained `RoomsService` scalar read can group messages by recipient, compare each delivery with the existing cursor, and return only a count, preserving the service's prohibition on exposing other recipients' message targets (`peerhub/governance/rooms.py:318-340`, `peerhub/governance/rooms.py:877-960`). No new per-message representation or denormalized counter is prerequisite. **Verdict:** this is no longer a major model blocker; it is a small read-model/API addition. The remaining design choice is real but narrow: room-only (simple native semantics), all retained rooms (closer to legacy `new-topic`), or a new mailbox epoch/reset boundary (needed for exact `clear-room` parity, because native `clear_room()` retains the old room and its messages). The `peerhub.status.read` contract should authorize only this aggregate scalar, never raw cross-recipient inbox rows.

#### Unread-mailbox aggregate concrete design (cx.deepthink, 2026-09-01)

**Legacy contract, precisely.** `status` reads `mailbox.json.unread_count` with a missing-value default of zero and applies no room or caller/recipient filter (`P:/_sys/core/hub.py:1680-1704`). The scalar is the number of *currently retained mailbox records* whose mutable `status` is exactly `"unread"`: `send` creates one record for its primary `to` recipient and recomputes the scalar; its `cc` list is metadata on that one record, not additional unread deliveries (`P:/_sys/core/hub.py:1503-1521`). `broadcast` creates one such record per target by calling `send` once per target (`P:/_sys/core/hub.py:1530-1569`). `mark-read` changes only unread records whose primary `to` matches the named target (all of them or one message ID) and then recomputes the same global scalar (`P:/_sys/core/hub.py:1572-1583`). This is neither a per-recipient count nor an unread-since cursor calculation. It is also more exact to say "currently retained" than "since the last clear": `send` can discard expired records under priority TTL policy and can evict records at the mailbox-size ceiling before recomputing the count (`P:/_sys/core/hub.py:1413-1434`, `P:/_sys/core/hub.py:1503-1521`). `new-topic` does not touch the mailbox, while `clear-room` archives and replaces it with an empty mailbox, so the former preserves the count and the latter resets it to zero (`P:/_sys/core/hub.py:3540-3573`, `P:/_sys/core/hub.py:3576-3586`).

**Native source and exact calculation.** Keep the read in `RoomsService`, adjacent to `check_inbox()` and `mark_read()`, because that service owns both sides of the native unread definition. `send_message()` writes one durable `inbox-message` target scoped to `room_id`, with one recipient identity and a sequence allocated per `(room_id, recipient_instance_id, recipient_profile_id)` stream (`peerhub/governance/rooms.py:209-300`). `mark_read()` stores that stream's monotonic `read_through_sequence` in the deterministic `inbox-cursor:{room_id}:{instance_id}:{profile_id}` target (`peerhub/governance/rooms.py:344-417`, `peerhub/governance/rooms.py:877-887`). Both are canonical JSON rows in `governed_targets`; migration 0025 added the transactionally maintained `target_kind`/`target_scope` projection and covering index used for these reads (`peerhub/persistence/migrations/0001_phase1_kernel.sql:13-18`, `peerhub/persistence/migrations/0025_governed_target_listing.sql:3-14`). The broker can list each target family by exact room scope in stable target order; `scope=None` deliberately means all scopes, so this method must pass the room ID rather than accidentally performing a workspace-wide scan (`peerhub/governance/broker.py:429-437`, `peerhub/persistence/sqlite_governance.py:48-82`).

Proposed public signature:

```python
def count_unread_messages(self, *, room_id: str) -> int
```

The method first requires the room to exist, lists that room's `inbox-cursor` targets into a map keyed by the exact recipient identity pair, then lists that room's `inbox-message` targets and counts each delivery row whose `sequence` is greater than its recipient's cursor (default cursor zero). It must count rows, not compute `max(sequence) - read_through_sequence`: the current sender explicitly documents that concurrent delivery writers can allocate the same sequence, and retained streams can therefore contain duplicates or gaps (`peerhub/governance/rooms.py:247-263`). A broadcast delivery to three recipients consequently contributes three until their respective cursors advance. The eventual status coordinator wraps the scalar as `{"unread_count": count}` and renders `**Mailbox**: <count> unread`; it does not receive recipient identities, message bodies, or a per-recipient breakdown. That keeps cross-recipient visibility confined to the aggregate instead of bypassing `check_inbox()`'s recipient-read boundary (`peerhub/governance/rooms.py:302-342`). Like `check_inbox()`, which reads the cursor and deliveries through separate broker calls, this is a convergent dashboard read rather than a cross-family linearizable snapshot; a concurrent send or cursor advance may appear on the next read, and no new locking or denormalized counter is justified for this status scalar (`peerhub/governance/rooms.py:318-342`).

**Scope and reset decision: room-scoped aggregate, no mailbox epoch.** This is a deliberate native adaptation, not a claim that legacy was room-scoped. PeerHub supports independently retained rooms, and every delivery and cursor already carries an exact room scope. Counting `list_targets("inbox-message", None)` would mix unrelated concurrent rooms and would continue counting an old room after a clear. Instead, `peerhub.status.read` must pass its resolved `room_id` to `count_unread_messages()`. Native `new-topic` is implemented as `create_thread()` inside the same room, so it naturally preserves that room's unread count (`peerhub/application/api.py:599-600`, `peerhub/application/api.py:764`). Native `clear_room()` creates a fresh room while deliberately retaining the old target and history; querying the fresh room therefore starts at zero without deleting evidence (`peerhub/governance/rooms.py:139-160`, `tests/integration/governance/test_rooms_threads.py:54-84`). An old room remains explicitly queryable and retains its own unread count, which is consistent with PeerHub's durable multi-room model even though legacy destroyed the live mailbox view. A truly workspace-global legacy-compatible count across topic-created room IDs would require a new mailbox-epoch target carried by every delivery and rotated by `clear_room`; that would add writes to `send_message()` and `clear_room()` and is rejected for the native status contract because it weakens room isolation to reproduce a retired singleton-file constraint.

**Read/reset semantics.** No new write path is needed. `check_inbox()` remains a non-advancing read (`peerhub/governance/rooms.py:302-342`). Existing `mark_read()` is the sole reset mechanism within a room/recipient stream: advancing its high-water cursor makes every delivery at or below that sequence cease contributing to the aggregate, while later deliveries with greater sequences count again (`peerhub/governance/rooms.py:344-417`). This follows PeerHub's already-shipped high-water semantics, including the documented difference from legacy's sparse out-of-order single-message acknowledgement (`peerhub/governance/rooms.py:352-357`); the aggregate must not invent per-message read flags to regain that old behavior. `clear_room()` provides the room-level reset by changing which room status queries. Calling the aggregate itself is purely read-only and must create no cursor, event, counter, or receipt.

**Sizing and proof target.** This is small enough for one focused implementation round: one read-only `RoomsService` method and SQLite-backed tests, with no migration, coordinator, or new command required. The minimum proof should cover two recipients in one room, cursor advancement reducing only the matching recipient's contribution, a later delivery becoming unread again, another room being excluded, the fresh room after `clear_room()` reporting zero while the retained old room remains independently countable, and repeated aggregate reads creating no targets. Landing this method closes only the mailbox row of `status`; it does not unblock the separate room-summary, ambient-room, or process-sweep decisions identified below.

**3. Ambient "current room" -- NOW SMALLER/TRACTABLE at the compatibility boundary, but truly empty input still has no native selector.** Legacy's rule is exact: resolve one workspace `.ai` root from `HUB_AI_ROOT`, the nearest CWD ancestor with `.ai`/`.git`, or the portable root fallback (`P:/_sys/core/hub.py:146-187`); `init-session --room` overwrites that workspace's single `state.room_id`, otherwise it creates one only when absent (`P:/_sys/core/hub.py:1362-1383`); and the no-argument `status` dispatch simply reads that scalar (`P:/_sys/core/hub.py:11902-11911`, `P:/_sys/core/hub.py:12064-12077`, `P:/_sys/core/hub.py:1680-1687`). It is not per-peer or inferred from mailbox activity.

PeerHub already has the two useful hooks. `RuntimeContext.workspace_home_id` identifies the current workspace (`peerhub/core/context.py:56-67`), and `_legacy_room_id()` already resolves `room_id` / `room` / `current_room` from action arguments, nested context, submission scope, or nested scope context (`peerhub/application/legacy.py:65-88`). Thus a legacy `status` call with no action argument but a room-bearing envelope can reuse an existing rule. What PeerHub does **not** have is a one-room-per-workspace invariant: room sessions store both workspace and room IDs (`peerhub/dispatch/room_session.py:57-70`), their active-session lookup requires the room ID up front (`peerhub/dispatch/room_session.py:311-332`), and the uniqueness constraint includes `room_id`, permitting the same identity to be active in multiple rooms (`peerhub/persistence/migrations/0028_room_participation_sessions.sql:20-39`). `_legacy_room_id()` returns an empty string when none of its contextual sources supplies a room (`peerhub/application/legacy.py:80-88`). **Verdict:** freeze a small compatibility policy rather than redesign RoomsService--prefer context/scope, then either fail clearly when absent, accept a unique-live-room fallback, or add an explicit workspace-current-room pointer if strict shell parity is required. The helper makes the first half ready; silently choosing among multiple rooms remains unjustified.

#### Ambient current-room concrete design (cx.deepthink, 2026-09-01)

**Legacy rule, precisely.** The legacy action has no room parameter at its handler boundary: main resolves exactly one `.ai` root, calls `action_status(ai_root)`, and that handler reads `state.json.room_id` (`P:/_sys/core/hub.py:1679-1687`, `P:/_sys/core/hub.py:12056-12077`). Workspace selection and room selection are separate. `--ai-root` first pins `HUB_AI_ROOT`; otherwise `find_ai_root()` uses a nonblank `HUB_AI_ROOT`, then the nearest CWD ancestor containing `.ai` (or `.git`), then the portable repository's canonical `.ai` fallback (`P:/_sys/core/hub.py:146-187`, `P:/_sys/core/hub.py:12008-12011`). Inside that chosen workspace, `state.room_id` is a single durable pointer initialized to null (`P:/_sys/core/hub.py:599-617`). `init-session --room` overwrites it, an init without `--room` preserves a nonempty value or creates one only when absent, and `end-session` does not clear it (`P:/_sys/core/hub.py:1362-1396`). `new-topic` and `clear-room` also overwrite it with their fresh room IDs (`P:/_sys/core/hub.py:3540-3573`, `P:/_sys/core/hub.py:3576-3598`). There is no last-activity query, active-session inference, or per-recipient default. Even though the legacy parser globally accepts `--room`, the `status` dispatch does not pass it; if the pointer is null, status simply renders its missing-room placeholder rather than selecting or creating a room (`P:/_sys/core/hub.py:11902-11911`, `P:/_sys/core/hub.py:12064-12077`, `P:/_sys/core/hub.py:1685-1687`).

**What the existing PeerHub resolver does--and does not do.** `_legacy_room_id(arguments, scope)` is an envelope extractor, not an ambient-state resolver. Its fixed precedence is: direct `room_id` / `room` / `current_room` / `current-room`; the same aliases under `arguments.context`; the submission scope; then `scope.context`; otherwise `""` (`peerhub/application/legacy.py:65-88`). Today its only production call site is the `alert-raise` translator (`peerhub/application/legacy.py:1656-1665`), with a real integration test proving nested `context.current_room` resolution (`tests/integration/test_stage2_boundary.py:2304-2319`). It never reads `RuntimeContext`, governed room targets, room-participation sessions, or a persisted pointer. Consequently it does not solve truly empty input for this or any other action; `alert-raise` ultimately rejects an empty room through `require_text()` (`peerhub/application/alert_raise.py:56-67`). `RuntimeContext.workspace_home_id` identifies the database/workspace only and contains no room association (`peerhub/core/context.py:56-67`).

**Resolution: require explicit room identity; do not create a workspace-current-room target.** The native `peerhub.status.read` contract should require one nonempty `room_id` parameter. Its eventual typed command/coordinator shape is `StatusReadCommand(..., room_id: str)` -> `read_status(*, room_id: str)`, with existence/kind validation delegated to the room service just as other room reads do (`peerhub/governance/rooms.py:1001-1007`). At the legacy boundary, the `status` translator should call `_legacy_room_id(call.arguments, submission.scope)`: a resolved contextual/scope value becomes the command's required `room_id`; an empty result returns `InvalidLegacyArguments(action="status", reason="room_id is required in arguments, context, or scope")` before any service read or mutation. This deliberately waives the raw shell's singleton-pointer default while preserving no-argument *action payloads* when the surrounding submission already carries room context. The existing native CLI is the correct precedent: `peerhub room status` requires `--room-id` and then reads exactly that target (`peerhub/cli.py:1514-1522`, `peerhub/cli.py:2489-2507`).

A new `current-room:workspace` target would be the wrong fix. PeerHub permits simultaneous rooms: room records remain `status="active"`, `clear_room()` retains the old room unchanged, and the same participant identity may hold active sessions in multiple rooms because `room_id` is part of the uniqueness key (`peerhub/governance/rooms.py:82-101`, `peerhub/governance/rooms.py:139-160`, `peerhub/persistence/migrations/0028_room_participation_sessions.sql:20-39`). A last-writer-wins pointer would make one terminal's init/clear silently redirect another terminal's status, while a “latest room,” “only active room,” or stable-order fallback would become ambiguous as soon as two retained/active rooms exist. Adding the pointer would also force unrelated session and room lifecycle writers to maintain a compatibility projection. Failing clearly is therefore more deterministic and consistent with PeerHub's explicit-scope model than recreating the legacy singleton-file quirk.

**Sizing and completeness.** The ambient-room design is complete and implementation-ready as a small boundary change: no migration, new service, or new write path; tests need only cover the resolver precedence, a contextual/scope success, and a truly empty `status` returning `InvalidLegacyArguments` with zero effects. The full catalogued `status` action is **not** unblocked. The authoritative mission/blocked/phase/updated-at room summary still has no SSOT/writer, and the required implicit process-lease sweep still lacks expired-lease enumeration, process observation/reaping orchestration, and its health consequence (blockers 1 and 4 above/below). The catalog currently maps `status` to `peerhub.status.read` but correctly falls through to `KnownLegacyActionNotBacked`; that must remain true until those semantics land or an explicit parity waiver is ratified (`peerhub/application/legacy.py:129-140`, `peerhub/application/legacy.py:1823-1830`).

A partial dashboard is a legitimate incremental **native** feature only under an explicitly non-parity surface. The existing `peerhub room status --room-id` could be enriched with the room record, leader/reason, live participants, roles, the proposed unread count, task/lock/active-consensus summaries, and bounded handoff, while returning explicit `complete: false` / `omitted_sections: ["room_summary", "process_lease_sweep"]` metadata in JSON. It must not register/translate `peerhub.status.read`, increment the 50/90 count, or present the legacy Markdown contract. The top-level `peerhub status` is already a different workspace/database/migrations/active-lease diagnostic (`peerhub/cli.py:1811-1824`, `peerhub/cli.py:2817-2856`), so overloading that name with an incomplete room report would add confusion. In this session's parity discipline, a documented partial native dashboard is useful; calling it the backed legacy `status` action would be misleading.

Process-lease sweep/reaper -- STILL GENUINELY BLOCKED; the landed bridge is adjacent, not the missing writer.** PeerHub still exposes only a by-ID lease read and a scalar active count; there is no expired-lease enumeration (`peerhub/persistence/sqlite_dispatch.py:1240-1250`, `peerhub/persistence/sqlite_dispatch.py:1337-1352`). Completing (2) and the small boundary work in (3) must not be counted as backing `status` until (1) and either (4) or an explicit process-sweep parity waiver are resolved.

#### Room-summary SSOT concrete design (ag.deepthink, 2026-09-01)

**Real legacy source and writers, precisely.** The `mission`, `blocked`, `phase`, and `updated_at` fields reside as room-level scalars directly on the workspace `state.json`. They are genuinely never touched by anything peerhub has built.
1. `action_update_status` (`P:/_sys/core/hub.py:1608-1617`) performs a partial update: unconditionally sets `mission`, sets `blocked` and `phase` only if provided, and refreshes `updated_at`.
2. `action_new_topic` (`P:/_sys/core/hub.py:3563-3566`) and `action_clear_room` (`P:/_sys/core/hub.py:3595-3598`) unconditionally set `mission=subject`, `blocked=None`, `phase="new-topic"` (or `"clear-room"`), and refresh `updated_at`.
3. `action_alert_raise` (`P:/_sys/core/hub.py:8995-8996`) overwrites `blocked` with the alert message and refreshes `updated_at`.
Legacy `action_status` (`P:/_sys/core/hub.py:1701-1704`) reads exactly these four fields to display the room's situation. Furthermore, `phase` is heavily load-bearing for security guards: the Operational Guard Matrix (`P:/_sys/core/hub.py:9106-9402`) relies entirely on `_current_phase()` to enforce `phase_action_matrix` policies and tier-0 boundaries. 

**Native TargetState shape: a new `room-summary` target family.** `RoomsService` currently models the main `room:{room_id}` target as static after creation, deferring mutations to separate targets like `room-goal` (`peerhub/governance/rooms.py:598-626`). Expanding `room` or `room-goal` to hold highly-mutated status fields would create CAS contention and mix lifecycles. Instead, `mission`/`blocked`/`phase` require their own small, dedicated target family: `room-summary:{room_id}`.
Its state will contain: `room_id`, `mission`, `blocked`, `phase`, and `updated_at`. `RoomsService` needs one new mutating method `update_room_summary(...)` that applies partial updates (matching legacy `update-status`), clears `blocked` on `new-topic`/`clear-room`, and applies the alert message on `alert-raise`.

**Honest sizing and `status` readiness.** This is definitively a small task: one target family schema and a single `RoomsService` mutation method. However, **this is NOT the last blocker for a fully native `status`**. While tasks, roles, leadership, participants, consensus, and handoff are natively modeled, legacy `action_status` (`P:/_sys/core/hub.py:1680`) explicitly calls `_lease_sweep(ai_root)` *before* reading state. As noted above in the status re-assessment, the process-lease sweep/reaper (item 4) remains genuinely blocked. Resolving the `room-summary` SSOT will close the final *data* model gap for `status`, but `status` will still remain blocked from full parity until the `process-lease sweep` side-effect is built or explicitly waived.

### Manual-quarantine authorization policy PROPOSED (2026-08-30)

**Recommendation: Option C (Budget-gated administrative authorization with authority-class matching).**

Instead of inventing a new RBAC privilege system (which peerhub does not have) or dangerously overloading the automated `authorize_recovery()` path to ignore cooldowns, we should follow the established permission pattern from `arbiter-review`: **budget gating**. Furthermore, we borrow the state-based protection pattern from `LeadershipService` (which protects incumbents based on state) by using a **QuarantineAuthorityClass precedence ladder** (`AUTOMATIC < MANUAL < POLICY < SECURITY`).

**Design:**
Create a distinct, explicitly-named method on `HealthService`:
`authorize_administrative_recovery(self, instance_id: str, profile_id: str, scope: PolicyScope, subject: str, *, authorized_by: str, target_authority_class: QuarantineAuthorityClass) -> RecoveryProbeAuthorization`

1. **Preconditions & Authorization:**
   - Evaluates the circuit's existing `quarantine_authority_class` against the requested `target_authority_class`. If the circuit's class dominates the requested class (e.g., circuit is `SECURITY` but caller asserts `MANUAL`), reject it. This protects higher-order quarantines without needing RBAC user roles.
   - Bypasses the `AdmissionState.RECOVERY_REQUIRED` check. Because this is an explicit administrative override, it accepts `QUARANTINED` (manual) and `COOLDOWN` (automatic) circuits.
   - **The Budget Gate:** To prevent probe-spam abuse, it must acquire a slot from an `AdministrativeRecoveryBudgetManager` using the already-defined `policy.administrative_recovery_probe_limit` (fulfilling the deferred check noted in `peerhub/health/model.py`'s `authorize_recovery_probe`). If the budget is exceeded, the authorization is rejected.

2. **State read/written:**
   - Reads the existing projection, circuit, policy, and a new CAS-backed budget target (e.g., `health-budget:administrative-recovery`).
   - Writes the budget consumption, inserts the unconsumed `RecoveryProbeGrant` (1 probe), and CAS-updates the projection to `PROBE_AUTHORIZED` via the existing `reduce_authorize_recovery()` pure reducer.

3. **Success vs. Failure Pipeline Interaction:**
   - This keeps the *authorization* paths fully separate (automated sweeps call `authorize_recovery` and respect cooldowns; operators call `authorize_administrative_recovery` and spend budget).
   - Once authorized, it feeds into the **exact same recovery pipeline**. The grant is claimed via `claim_recovery_probe` and evaluated via `apply_recovery_probe_result`.
   - On probe success, the reducer transitions the circuit to `CIRCUIT_CLOSED`, safely lifting the manual quarantine *because real health evidence was provided*.
   - On probe failure, the grant is exhausted, backoff increments, and the circuit's state re-evaluates (remaining `QUARANTINED` since its authority class is unchanged).

**Tradeoffs of alternatives considered:**
- **Option A (Distinct gate with just an operator reason):** Fails to mitigate the risk of probe-spam/abuse without a budget limit, and doesn't explicitly handle hierarchical quarantines (like `SECURITY` vs `MANUAL`).
- **Option B (Extending `authorize_recovery` to accept `QUARANTINED`):** Blurs the lines dangerously. An automated `health-sweep` could accidentally lift a manual quarantine if it just scanned for all non-open circuits, and applying budget logic conditionally inside a single method creates branching hazards.

**Explicitly OUT of scope for this decision:**
- The design and placement of the `HealthRevalidationCoordinator` (the application-layer piece that actually executes the probe).
- The definition of the exact budget window duration (requires its own policy configuration like `arbiter-review`'s 5-hour window).
- Any "break-glass" mechanism to write `HEALTHY` directly without a probe. As ratified in `docs/design/phase0/RUNTIME-HEALTH-DRIFT-2026-07-28.md` (lines 45-55), recovery *cannot write HEALTHY directly*; it must produce a successful probe.

#### Critique (cx.deepthink, 2026-08-30)

Independent verification verdict: **REVISION REQUIRED BEFORE RATIFICATION.** The proposal correctly identifies the manual-quarantine deadlock and the right high-level shape (a distinct administrative entry point feeding the existing receipt-fenced probe pipeline, never a direct healthy write), but its proposed authority check is self-asserted rather than authorized, and the current aggregate projection logic would make the new path inoperative even after it persisted a grant.

1. **`QuarantineAuthorityClass`: TYPE CONFIRMED; PRECEDENCE LADDER REFUTED AS EXISTING SUBSTRATE.** The real enum contains all four names, but it is an unordered `str, Enum`, declared `AUTOMATIC`, `MANUAL`, `SECURITY`, `POLICY` (`peerhub/health/contract.py:157-163`). No rank map or dominance operation exists; current reducers only distinguish `AUTOMATIC` from every other class (`peerhub/health/model.py:517-525`, `peerhub/health/model.py:701-709`). Thus `AUTOMATIC < MANUAL < POLICY < SECURITY` is a new policy rule, not something already supplied by the type (and even differs from declaration order, which is not semantic ordering anyway). The existing frozen statement is that manual/security/policy quarantines require their *designated authority* (`docs/design/PHASE1-KICKOFF-R1.md:56-67`), which supports an explicit clearance matrix or exact-class rule more directly than a total order. If cross-class dominance is wanted, it must be separately justified and tested.

2. **`administrative_recovery_probe_limit`: CONFIRMED REAL FIELD, BUT NOT A COMPLETE BUDGET CONTRACT.** `HealthPolicy` defines and positively validates it (`peerhub/health/contract.py:191-205`, `peerhub/health/contract.py:258-265`), SQLite persists it (`peerhub/persistence/migrations/0005_health_routing.sql:10-21`, `peerhub/persistence/sqlite_health.py:105-110`), and the reducer's deferred comment is real (`peerhub/health/model.py:554-565`). The reducer performs no check. No field defines the limit's time window, reset rule, scope (workspace/principal/circuit), reservation lifetime, or failure accounting. Declaring the budget-window duration out of scope while making that budget the safety gate leaves the gate unimplementable. Ratification must at least freeze those semantics and add a versioned window field (or deliberately define a different non-window budget).

3. **RECOVERY FUNCTIONS CONFIRMED, WITH NAMING CORRECTIONS.** The pure reducer is actually `authorize_recovery_probe()`; `reduce_authorize_recovery` is only its import alias inside `service.py` (`peerhub/health/model.py:554-592`, `peerhub/health/service.py:60-64`). The pure `claim_recovery_probe()` and `apply_recovery_probe_result()` functions are real and implement single-use claim plus receipt/revision-fenced failure/success transitions (`peerhub/health/model.py:595-668`). The public service methods are named `claim_probe()` and `apply_probe_result()`, and add transactional CAS/receipt checks (`peerhub/health/service.py:1186-1246`, `peerhub/health/service.py:1248-1315`). A current successful receipt closes the circuit regardless of authority class, so the administrative authorization boundary must itself be trustworthy.

4. **DEADLOCK CONFIRMED; THE PROPOSED BYPASS IS NECESSARY IN PRINCIPLE BUT NOT SUFFICIENTLY SAFE.** A non-automatic open circuit always evaluates to `QUARANTINED`, with no retry boundary, whereas only an automatic circuit can advance through `COOLDOWN` to `RECOVERY_REQUIRED` (`peerhub/health/model.py:694-735`). `HealthService.authorize_recovery()` accepts only `RECOVERY_REQUIRED` (`peerhub/health/service.py:1120-1133`). A distinct way to authorize a measured probe for a non-automatic quarantine is therefore required. However, a caller-supplied `target_authority_class` is not proof: any caller can assert `SECURITY` and dominate every proposed class. The comparison prevents only an accidentally low assertion, not an unauthorized high one. Budgeting limits frequency; it does not confer authority.

5. **REFUTED: THE EXISTING PROJECTION PIPELINE CANNOT YET REPRESENT THIS ADMINISTRATIVE GRANT.** `_aggregate_for_pair()` treats a live grant as `PROBE_AUTHORIZED` only when the same circuit already evaluates to `RECOVERY_REQUIRED` (`peerhub/health/service.py:585-601`). `_recompute_pair()` then overwrites the reducer seed's admission state with that aggregate (`peerhub/health/service.py:681-743`). Consequently, a grant issued while the circuit is `QUARANTINED` would recompute straight back to `QUARANTINED`; one issued while automatic cooldown is active would recompute to `COOLDOWN`. Avoiding recomputation would leave other members of a shared scope inconsistent and a later recomputation would revert the seed. The grant and aggregate contracts need a durable administrative-authorization marker (including authorized circuit revision/authority evidence), and aggregate validity must recognize that marker while still invalidating it on circuit escalation or receipt/revision change. `RecoveryProbeGrant` currently stores neither authorization mode nor authorized circuit revision (`peerhub/health/contract.py:736-747`).

6. **A GLOBAL BUDGET DOES NOT PROVIDE PER-CIRCUIT SINGLE-FLIGHT OR PACING.** Persistence enforces only one *unconsumed* grant per circuit (`peerhub/persistence/migrations/0006_recovery_probe_single_flight.sql:1-10`; `peerhub/persistence/sqlite_health.py:576-587`). As soon as a grant is claimed, another can be issued before the first result arrives. Revision fencing makes later results stale but does not prevent several provider probes from running. On a manual failure, `backoff_count` increments, yet non-automatic evaluation ignores that backoff and stays permanently `QUARANTINED` (`peerhub/health/model.py:644-655`, `peerhub/health/model.py:701-709`). The revision needs a per-circuit unresolved-attempt lease/single-flight rule and a next-administrative-probe boundary (or equivalent cooldown) in addition to an aggregate budget. It must define recovery from an abandoned claimed probe so the circuit is not locked forever.

7. **ACCEPTING `COOLDOWN` IS UNJUSTIFIED SCOPE EXPANSION.** The identified deadlock concerns non-automatic `QUARANTINED` circuits. Automatic circuits already reach `RECOVERY_REQUIRED` after the policy backoff (`peerhub/health/model.py:711-735`). Letting ordinary administrative authorization bypass `COOLDOWN` weakens that separate pacing policy without being necessary to solve the blocker. Exclude `COOLDOWN` from the first policy, or ratify an explicitly stronger early-retry/break-cooldown capability with its own authority and pacing semantics.

8. **SEPARATE PUBLIC PATHS ARE SOUND; FULLY DUPLICATED END-TO-END LOGIC IS NOT. OPTION B'S REJECTION IS PARTLY OVERSTATED.** Keep `authorize_recovery()` and `authorize_administrative_recovery()` as distinct public APIs so automated sweeps cannot opt into administrative behavior accidentally. Both should delegate to one internal authorization transaction/helper for configured-pair membership, projection policy/baseline, circuit/receipt/revision validation, grant conflict, grant construction, member recomputation, and fault boundaries; only the admission/authority/budget precondition should differ. Naively allowing every `QUARANTINED` circuit in today's `authorize_recovery()` would indeed be unsafe. A single typed method requiring an unforgeable administrative authorization object for that branch could also be safe, however, so method branching is not itself the security defect. The decisive controls are authenticated authority evidence and impossible-to-accidentally-select call sites.

9. **`authorized_by` MUST NOT REMAIN FREE TEXT, AND `PeerRegistryService` IS THE WRONG VALIDATOR.** Today `RecoveryProbeGrant` merely requires `authorized_by` to be non-empty (`peerhub/health/contract.py:749-759`), and `HealthService` copies it without authentication (`peerhub/health/service.py:1146-1155`). `PeerRegistryService` resolves peer-node/profile inventory, not human or service principals (`peerhub/application/peer_registry.py:72-130`). The relevant existing boundary type is `AuthenticatedSubject`, which carries a verified opaque principal plus evidence source and has a fail-closed type check (`peerhub/core/identity.py:14-31`, `peerhub/core/identity.py:89-96`). Administrative recovery should accept/derive that subject at a trusted application boundary and separately obtain an unforgeable authority grant/capability mapping the subject to the permitted quarantine class. Persist the principal, evidence source, granted class, authorizer/receipt ID, and reason. Authentication alone still is not authorization; unsupported `POLICY`/`SECURITY` classes must fail closed until an issuer exists.

10. **BUDGET ATOMICITY AND PROBE-EVIDENCE TRUST NEED TO BE EXPLICIT.** A generic CAS governance target and health grant/projection writes do not become one transaction merely because both use CAS. Either make the budget a health-owned row updated in the same `StateStore` unit of work as the grant/projections, or use an application-layer reservation/consume/release/unknown protocol like the real `ArbiterBudgetManager` (`peerhub/application/arbiter_review.py:226-316`, `peerhub/application/arbiter_review.py:319-415`). Also, the current `RecoveryProbeReceipt` contract permits empty evidence references and `apply_probe_result()` trusts the typed receipt it receives (`peerhub/health/contract.py:872-916`, `peerhub/health/service.py:1248-1293`). Reusing this pipeline preserves fencing and the no-direct-healthy rule (`docs/design/phase0/RUNTIME-HEALTH-DRIFT-2026-07-28.md:52-55`), but “real health evidence was provided” is guaranteed only if the future revalidation coordinator is a trusted producer/verifier and raw success receipts are not exposed to untrusted callers.

**Required revision before ratification:** retain the two public authorization entry points and shared probe-result pipeline, but (a) freeze an explicit authority matrix rather than assume enum ordering; (b) replace caller assertion/free text with authenticated principal plus issued authority evidence; (c) initially admit only the needed non-automatic `QUARANTINED` case; (d) extend the durable grant/aggregate validity model for administrative origin, circuit revision, and authority escalation; (e) freeze budget window/scope/atomicity and add per-circuit unresolved-probe plus retry pacing; and (f) centralize common authorization mechanics in one internal helper. Required tests include forged higher-class assertions, MANUAL/POLICY/SECURITY cross-class cases, circuit escalation after grant, multi-member projection recomputation, claimed-but-unresolved contention/expiry, concurrent budget reservation, and rollback/unknown outcomes. With those corrections, Option C's overall shape is preferable; as written, it is not ready for ratification.

No further Tier 4 work queued for now, at the user's direction -- most of the remaining ~45 unbacked actions have turned out to be either real per-domain design work (`report-error`'s health-authority bridge, `elect-leader`'s capability-scoring, `status`'s cross-domain aggregation) or host-level tooling this session has now repeatedly and consistently found doesn't belong in peerhub's domain model at all (8 confirmed instances across three separate scouting rounds: `freshness-sweep`, `append-log`, `archive-file`, `preflight`, `context-hash`, `profile-validate`, `transient-scan`, `update-signatures`). The clearest remaining tractable item, if picked back up, is `report-error`'s append-and-count half (the auto-quarantine half needs the same health-authority-bridge design work already identified as blocking).
- **Host-level / P:-environment-specific** (5 actions, **worth questioning whether these belong in peerhub's domain model at all**): `directive-add/list/clear`, `credit-status`, `credit-consume` — these read like they're about the P: portable environment's own host integration, not a generic peerhub concept. Resolve "does peerhub own this or does it stay host-side" before designing, not after.

### Alert scouting (2026-08-30): `alert-raise` is a real, small room-coordination gap — not health/error alerting and not host tooling

Research-only round (cx.deepthink; no implementation). **Verdict: (b), a genuine new but small/self-contained PeerHub gap.** It is not already covered by `OperationalErrorService`, `FeedbackService`, or `HealthService`, and it is not a host-side false friend: the action mutates the shared room/session record and delivers peer-to-peer inbox messages. The catalog already maps it to `coordination.alert.raise`, but there is no translation/service branch, so it still reaches the generic known-but-unbacked result (`peerhub/application/legacy.py:183`, `peerhub/application/legacy.py:1642-1645`).

**Real legacy behavior, including two important corrections to the ledger's interpretation.** The current handler accepts an implicit current room, `agent`, `severity`, and `msg`; the CLI defaults to `agent="unknown"`, `severity="P1"`, and an empty message, and only `P0`/`P1` (case-insensitive) pass validation (`P:/_sys/core/hub.py:8977-8981`, `P:/_sys/core/hub.py:12139-12140`; parity ledger: `docs/design/PHASE1-PARITY-LEDGER-BATCH5-2026-08-20.md:140-142`). It is mutating and deliberately non-idempotent. Under the `state` lock it reads `state.json`, snapshots every key in `state.members`, creates a fresh short alert ID, and overwrites the one `state.alert_active` slot with `{id, ts, severity, from, msg, status:"OPEN", ack_pending:[all member keys]}`; it also sets the human-readable `state.blocked` marker and `updated_at`, then atomically rewrites `state.json` (`P:/_sys/core/hub.py:8983-8997`; `_write_state` is the validated atomic `state.json` writer at `P:/_sys/core/hub.py:1089-1091`). A later raise replaces the prior active slot rather than deduplicating or appending another alert.

After the state commit, the handler prints its P2P/banner output and calls `action_send` once for every member other than the raiser, with body `[CRITICAL-ALERT] {severity}: {msg}`, `msg_type="ALERT"`, and `priority="CRITICAL"` (`P:/_sys/core/hub.py:8999-9005`). Those are local durable mailbox deliveries — `action_send` appends recipient-addressed records to `mailbox.json` and writes their per-message Maildir copies (`P:/_sys/core/hub.py:1503-1524`) — not an external pager, human notification API, or host integration. State commits before fan-out, so a send failure can leave the alert durable with only a partial recipient fan-out; there is no cross-file transaction (`P:/_sys/core/hub.py:8994-9005`).

The first ledger correction: its claim that `_log_p2p("ALERT-RAISE", ...)` persists a new `log.jsonl` event is not true of the current requested source. `_log_p2p` only formats a line to stderr (`P:/_sys/core/hub.py:1131-1142`), and `action_alert_raise` calls no append/journal helper (`P:/_sys/core/hub.py:8997-9005`). The ledger makes the stronger `log.jsonl` claim at `docs/design/PHASE1-PARITY-LEDGER-BATCH5-2026-08-20.md:144,153`; that effect should not be ported from the ledger alone.

The second correction: “blocks all governance workflows” is a docstring/ledger interpretation, not an enforced legacy gate. In real source the alert only writes `state.blocked`; that field is rendered by `status` and included in ask context (`P:/_sys/core/hub.py:1701-1704`, `P:/_sys/core/hub.py:2435-2440`), while no command admission path reads it. Generic `update-status` can clear the marker, and `new-topic`/`clear-room` clear it as a side effect (`P:/_sys/core/hub.py:1608-1615`, `P:/_sys/core/hub.py:3561-3567`, `P:/_sys/core/hub.py:3593-3599`). None of those paths changes `alert_active`. There is likewise no alert ACK/resolve action, and `ack_pending` has no reader or mutator anywhere in the current `hub.py`; `status:"OPEN"` and `ack_pending` are inert creation-time fields (`P:/_sys/core/hub.py:8985-8995`; the CLI action inventory at `P:/_sys/core/hub.py:11905` contains `alert-raise` but no alert acknowledge/resolve command). Therefore legacy is **durable raise-and-notify with overwrite-on-next-raise**, not fire-and-forget, but it has no functioning `OPEN -> ACKNOWLEDGED -> RESOLVED` lifecycle and no real circuit breaker.

**Existing-substrate verdict — useful building blocks exist, but no service already covers the concept.**

- `OperationalErrorService` is a per-`(peer_key, pattern)` append-and-count series; at or above a pinned threshold it creates an immutable `quarantine-review` request and explicitly leaves health circuit state to the health domain (`peerhub/governance/operational_errors.py:1-7`, `peerhub/governance/operational_errors.py:102-111`, `peerhub/governance/operational_errors.py:178-201`, `peerhub/governance/operational_errors.py:224-249`). `alert-raise` has no pattern counter, threshold, review request, or peer-health subject, and it must notify the live room immediately. Reusing this service would invent escalation semantics and still miss both the room marker and fan-out.
- `FeedbackService` is a multi-item journal with sequential `GAP-*` IDs, per-item `status`/`owner`, list, and resolve operations (`peerhub/governance/feedback.py:36-49`, `peerhub/governance/feedback.py:111-170`, `peerhub/governance/feedback.py:172-227`). Its superficially similar severity/detail fields do not make it an alert: it has no active-room singleton, live-member snapshot, blocking marker, or notification. Encoding an alert as feedback would erase the action's coordination semantics.
- `HealthService` owns policy-derived health/admission circuits, not arbitrary emergency messages. Opening a circuit requires a typed failed `HealthStageObservation` trace plus `EvidenceSubject` and `PolicyReceipt`, then updates the affected health scope and projections atomically (`peerhub/health/service.py:259-279`, `peerhub/health/service.py:925-1002`). Recovery is receipt-fenced and circuit-specific (`peerhub/health/service.py:1004-1045`, `peerhub/health/service.py:1081-1184`). A free-form P0/P1 room alert has none of that evidence or subject identity, and legacy does not actually change health/admission state. Calling HealthService would repeat the authority-model error already rejected for forced `peer-quarantine`.
- The real reusable pieces are coordination substrate. `RoomParticipationCoordinator.list_active_sessions(room_id)` returns the heartbeat-fresh live sessions that most closely correspond to legacy `state.members` (`peerhub/dispatch/room_session.py:311-349`); this is a better recipient source than `RoomsService.list_participants()`, whose own contract says it is the room's immutable participant snapshot (`peerhub/governance/rooms.py:46-61`). `RoomsService.send_message()` already persists one private room-scoped `inbox-message` per recipient, with `message_type`, resource reference, and shared correlation ID (`peerhub/governance/rooms.py:209-296`). `LessonBroadcastCoordinator` is the structural precedent for an application-layer coordinator that records one governed campaign and then fans out through `RoomsService` (`peerhub/application/lesson_broadcast.py:30-52`, `peerhub/application/lesson_broadcast.py:63-128`), although its immutable-participant recipient rule must not be copied for this live-member action.

The older gap-6 draft is not a ready-made parity design. It proposed evidence-derived/deduplicated alerts and a broad `OPEN -> ACKNOWLEDGED -> UNDER_REVIEW -> ... -> RESOLVED` lifecycle (`docs/design/HUB-REPLACEMENT-GAP6-GOVERNANCE-2026-08-24.md:104-114`, `docs/design/HUB-REPLACEMENT-GAP6-GOVERNANCE-2026-08-24.md:155-170`), while real legacy is non-deduplicated, accepts only severity/message/raiser, and implements no lifecycle after creation. The later ratification only settled policy for ownership and when an alert requires a proposal (`docs/design/HUB-REPLACEMENT-PRE-TDD-FINAL-RATIFICATION-2026-08-26.md:60-62`); it did not supply the missing schema, raise mechanics, or parity boundary. Treat that richer alert registry as possible future native scope, not as evidence that this standalone compatibility action is already covered.

**Critique-ready ratified candidate (not implemented and not declared final by this research pass).** Place `AlertRaiseCoordinator` in `peerhub/application/alert_raise.py`, because it coordinates three owners — governance targets, live room sessions, and inbox delivery — just as `LessonBroadcastCoordinator` lives in `application/` for cross-domain fan-out. Constructor: `AlertRaiseCoordinator(broker, *, rooms, room_sessions, clock, ids)`. Method: `raise_alert(*, room_id: str, raiser_instance_id: str, raiser_profile_id: str, severity: str = "P1", message: str = "") -> AlertRaiseResult`. Normalize severity to uppercase and reject anything outside `{P0,P1}`; deliberately permit the empty message because legacy does.

Persist one current-slot target, `target_id="room-alert:{room_id}"`, rather than one independently active target per raise. Its complete `TargetState.state` candidate is `{"kind":"room-alert", "scope":room_id, "schema_version":1, "room_id":room_id, "alert_id":..., "severity":"P0|P1", "message":..., "status":"OPEN", "raised_by":{"instance_id":...,"profile_id":...}, "raised_at":..., "ack_pending":(<snapshot of all live member identities, including the raiser if present>), "blocked":f"{severity} Alert: {message[:40]}...", "updated_at":...}`. This preserves the real singleton overwrite, visible block text, and inert compatibility fields without inventing acknowledgement semantics. Allocate the new alert ID/time once per logical call and retry a stale-revision CAS on this shared current slot with the existing bounded 16-attempt pattern: legacy's state lock serializes concurrent raises and allows every caller to commit, so simply surfacing the first CAS loss would be an avoidable parity regression. Refresh the live-session/revision snapshot on each CAS attempt and retain the winning snapshot for `ack_pending` and delivery, so a contended retry does not notify stale membership.

### `peer-registry` RATIFIED (2026-08-28): critique round (cc.deepthink) overturns cx's singleton, resolves the adapter-kind-safety question

**Schema, corrected from cx's singleton sketch: one `peer-node:{node_id}` target per node, not a `peer-registry:workspace` singleton.** Two reasons: the parity ledger's own comparator for `list-nodes` says ordering is explicitly NORMALIZED/out of contract, so `node_order` isn't needed (`list_targets` already gives deterministic `ORDER BY target_id`); and a singleton is the minority pattern in this codebase (5 of 6 broker domains use per-entity targets) reserved for genuine cross-entity invariants like `arbiter-budget:workspace`'s shared count/window -- node registration has no such invariant, so a singleton would force an unnecessary CAS-retry loop and make `list_targets` unusable. ### Locks (`file-lock`/`file-unlock`/`lock-status`) RATIFIED (2026-08-30): a genuine new durable lock domain, NOT built on DutyLeaseCoordinator

Research (ag.deepthink) against real Parity Ledger entries (`docs/design/PHASE1-PARITY-LEDGER-BATCH4-2026-08-20.md` §§4-6) confirms legacy file-locks are durable and non-expiring. They track a simple `locked_at` timestamp, do not require heartbeats, and are explicitly idempotent upon re-entry by the same owner (preserving the original timestamp). `DutyLeaseCoordinator` is strictly for room-scoped, TTL-expiring, heartbeat-renewed leases with automatic recovery. Forcing file-locks into `DutyLeaseCoordinator` would be the exact same "wrong reuse" trap that broke leadership. A new, distinct lock domain is genuinely needed.

**Placement**: `peerhub/governance/file_locks.py` (a workspace-global coordination registry, not an application-layer routing concern like duty leases).

**Schema**: A per-resource `file-lock:{name}` TargetState family.
State: `name` (the locked resource), `owner` (the holding peer/agent identity), `scope` (default "file"), `locked_at` (timestamp, preserved on idempotent re-entry), and `status` (`ACTIVE|RELEASED`).

**Methods**:
- `lock_file(name: str, owner: str, scope: str = "file")`: CAS on `file-lock:{name}`. If absent or `RELEASED`, create/update as `ACTIVE` with `locked_at = now`. If `ACTIVE` and `existing.owner == owner`, return existing unchanged (strictly idempotent, preserves original `locked_at`). If `ACTIVE` and `existing.owner != owner`, raise a lock conflict error.
- `unlock_file(name: str, owner: str | None = None)`: CAS on `file-lock:{name}`. If absent or `RELEASED`, no-op/warn. If `ACTIVE` and `owner` specified but `existing.owner != owner`, raise an ownership mismatch error. Otherwise, mutate to `status="RELEASED"`.
- `list_active_locks()`: Scans `file-lock:*` targets for `ACTIVE` locks to format the TSV output for `lock-status`.

**Cross-domain impact on `status`**:
Building this locks domain will unblock the locks-reporting portion of the legacy `status` action. However, as noted in this document's configuration/telemetry scouting section, `status` is a genuine multi-domain aggregation read (rolling state/mailbox/task-registry/locks/consensus into one report). While locks are a prerequisite, `status` will still require its own dedicated cross-domain wiring and design work once all its dependencies exist.

**5. Unlock semantics -- CONFIRMED, and there IS an admin-override path that the design reproduces but never states.**

- Absent lock: `[HUB:WARN] {name} is not locked` on **stdout**, bare `return`, **exit 0** (`P:/_sys/core/hub.py:11414-11416`). Confirmed.
- Explicit owner mismatch: exit 1, `[HUB:ERROR] {name} is locked by {existing.get('owner')}, not {owner}` (`P:/_sys/core/hub.py:11418-11419`). Confirmed.
- **The override, answering the critique question directly:** the guard is `if owner and existing.get("owner") != owner`. `owner` defaults to `""` and the CLI passes `args.peer or args.agent or ""` (`P:/_sys/core/hub.py:12228`), so `file-unlock --name X` with **no `--peer`/`--agent`** unconditionally force-releases *anyone's* lock, exit 0, with no authority check and no audit trace. So: an unrelated peer supplying its own identity is always rejected, but any caller willing to omit the identity flag can force-unlock. It is not a `--force` flag -- it is the absence of an argument, which makes it trivially reachable. ag's `owner: str | None = None` reproduces this correctly, but because the design text never calls it out, an implementer could very plausibly "harden" it into always-require-owner and break parity. **State it explicitly, with a dedicated test**: `unlock_file(name, owner=None)` against another peer's ACTIVE lock must succeed. Recommended strictly-additive improvement: since peerhub carries `actor_id` on every mutation (legacy does not), record the forcing actor as `released_by` in the RELEASED state -- parity-preserving, and it closes legacy's audit hole.

1. **BLOCKING -- the state schema omits `kind`, so `list_active_locks()` would silently return nothing.** `target_kind` is derived from `state["kind"]` and `target_scope` from `state["scope"]` at persist time (`peerhub/persistence/sqlite_governance.py:101-104`), and `list_targets` filters on the `target_kind` column (`peerhub/persistence/sqlite_governance.py:60-81`). Every sibling domain includes it: `role_assignment.py:217-219`, `operational_errors.py:187-189`, `alert_raise.py:94-96`. **Add `"kind": "file-lock"` and `"schema_version": 1`.**
2. **BLOCKING -- the domain's `scope` field name collides with the persistence partition key.** Per the same `sqlite_governance.py:102-104` derivation, putting legacy's free-text lock scope (`"file"`, or an arbitrary `--section` value) into `state["scope"]` writes it into the indexed `target_scope` partition column. Every sibling either sets a genuine coordination scope (`alert_raise`: `room_id`) or `None` (`feedback`, `role_assignment`, `operational_errors`). Locks are workspace-global and have no partition scope. **Set `"scope": None` and carry legacy's value under a distinct key such as `"lock_scope"`, mapping it back to the `scope` TSV column at presentation time.**
3. **Real parity miss -- `lock_file` cannot early-return-unchanged on same-owner re-entry.** Per finding 1 above, legacy updates `scope` on re-lock while preserving `locked_at`. The design's "return existing unchanged" makes a same-owner scope update a silent no-op. Re-submit when the normalized scope differs (preserving `locked_at`), or simply always re-submit with the preserved `locked_at`.
4. **Unstated-but-load-bearing -- the ownerless force-unlock** (finding 5). Must be written into the design text so it survives implementation.
5. **`list_active_locks()` ordering diverges, but is already sanctioned.** peerhub's `list_targets` is `ORDER BY target_id ASC` (`peerhub/persistence/sqlite_governance.py:66-69`), i.e. sorted by `file-lock:{name}`; legacy iterates acquisition order. The ledger already declares the comparator `NORMALIZED (ISO timestamps, lock entry iteration ordering)` (`docs/design/PHASE1-PARITY-LEDGER-BATCH4-2026-08-20.md:104`), so name-ASC is **within** the sanctioned normalization -- but say so in the design rather than leaving it to be discovered as a fixture failure, per the `fix-register-node-pos-01` lesson (line 305 above).

Take UTC from the injected `Clock` per house convention (line 185 above), and record it as a deliberate deviation; the ledger's comparator normalizes ISO timestamps anyway.
7. **`name` is a path and must be stored verbatim.** The ledger's own fixtures use `docs/spec.md` and `src/main.py`, and the CLI accepts `--name` or `--file` (`P:/_sys/core/hub.py:11934-11935`). `file-lock:docs/spec.md` is safe as a `target_id` -- IDs are opaque and `kind` is a separate column, nothing splits on `:` -- but note explicitly that legacy performs **no** path normalization, so `docs/spec.md`, `docs\spec.md`, and `./docs/spec.md` are three distinct locks. Do not "improve" this on a Windows-hosted workspace; normalizing would be a parity break.
8. **Return shapes are unspecified, and peerhub services do not print.** The "no-op/warn" wording has no peerhub equivalent. Follow the `RoleReleaseResult`/`RoleReleaseDisposition` precedent (`peerhub/application/role_assignment.py:24-33`): return a disposition (`RELEASED` / `NOT_LOCKED`) so the CLI emits `[HUB:WARN] {name} is not locked` at exit 0. Likewise `lock_file` should distinguish ACQUIRED from RE-ENTERED even though both print the identical `[HUB] FILE-LOCK {name} | owner={owner}` line.

### Manual-quarantine authorization policy REVISED (2026-08-30)

**Scope Correction:** This revised proposal addresses the deadlock specifically for manually-quarantined circuits. In accordance with the critique, we are explicitly removing the scope expansion that would have bypassed `COOLDOWN` for automatic circuits. The `authorize_administrative_recovery()` method will exclusively target non-automatic `QUARANTINED` circuits (i.e., those with `MANUAL` or higher authority class). Automatic circuits will continue to use the existing `authorize_recovery()` path unchanged.

**Design Updates:**

1. **Explicit Precedence Ladder Logic:**
   The `QuarantineAuthorityClass` enum does not natively provide dominance ordering. We will introduce a new pure comparison function in `peerhub/health/model.py` (e.g., `def dominates(a: QuarantineAuthorityClass, b: QuarantineAuthorityClass) -> bool:`) that explicitly encodes the hierarchy: `AUTOMATIC < MANUAL < POLICY < SECURITY`. This freezes the authority matrix rather than relying on enum declaration order.

2. **Durable Administrative Authorization Marker and Recomputation Fix:**
   To resolve the blocking bug where `_aggregate_for_pair` in `peerhub/health/service.py` reverted the projection, `RecoveryProbeGrant` will be extended to store `authorization_mode` (e.g., `AUTOMATIC` vs `ADMINISTRATIVE`) and `authorized_circuit_revision`. 
   The `valid_live_grant` check in `_aggregate_for_pair` must be modified to:
   - Require `live_grant.authorized_circuit_revision == circuit.revision`.
   - Treat the grant as `PROBE_AUTHORIZED` if it's an `AUTOMATIC` grant on a `RECOVERY_REQUIRED` circuit, **or** if it's an `ADMINISTRATIVE` grant on a `QUARANTINED` circuit. This explicitly instructs the recomputation logic to respect the administrative bypass and not silently revert to `QUARANTINED`.

3. **Authenticated Authorization Mechanism:**
   We will remove the caller-asserted `target_authority_class` string parameter. Instead, `authorize_administrative_recovery()` will accept an `AuthenticatedSubject` (from `peerhub/core/identity.py`) and a typed authority capability object (e.g., `QuarantineAuthorityCapability`) issued from a trusted application boundary. The capability maps the verified principal to a permitted `QuarantineAuthorityClass`. This provides real authorization matching the precedent set by role assignment and leader election, rejecting unsupported claims fail-closed.

4. **Budget Window and Per-Circuit Pacing:**
   The budget will be implemented as an anchored 5-hour window via an `AdministrativeRecoveryBudgetManager` (mirroring `ArbiterBudgetManager`), not just a loose limit field.
   - **Exhaustion:** If the budget is exhausted, the method will reject the attempt with a clear `budget_exceeded` error (no silent failures).
   - **Per-Circuit Pacing:** We will add a per-circuit single-flight lease/unresolved-attempt rule. If an administrative probe fails, a specific administrative cooldown (separate from the budget) must elapse before another administrative authorization can be attempted on that same circuit, effectively blocking operators from spam-retrying a failing probe.

5. **Shared Probe Pipeline:**
   `authorize_recovery()` and `authorize_administrative_recovery()` will remain distinct public APIs to prevent accidental sweeping. Both will delegate to a shared internal helper for transaction atomicity, fault injection, and grant/projection construction, avoiding duplicated core logic while keeping the entry points secure.

### Manual-quarantine authorization policy -- final resolution attempt (2026-08-31)

**Gap 1: Single-operator premise**
FINDING: The single-operator premise is TRUE. Investigation of `peerhub/core/identity.py` confirms that the system models identity via `AuthenticatedSubject`, which is populated by `LocalProcessCallerIdentityProvider` using the OS process owner (`psutil.Process().username()`). There is no concept of multiple distinct human principals with different privilege levels or RBAC roles anywhere in the identity model. The caller is simply "the authenticated local operator".

RESOLUTION: Gap (1) is cleanly resolved by this reframing. We can simplify `authorize_administrative_recovery()` to require only a valid `AuthenticatedSubject` as proof of authorization, eliminating the need for a separate `QuarantineAuthorityCapability`. The `QuarantineAuthorityClass` (AUTOMATIC < MANUAL < POLICY < SECURITY) will strictly describe the properties of the *quarantine itself* (e.g., higher-class quarantines cannot be lifted by lower-class administrative overrides) rather than the caller's privileges. Since there is only one operator class, any authenticated operator is permitted to spend from the administrative recovery budget. The design is now RATIFIED, READY FOR IMPLEMENTATION.

**Gap 2: Budget/lease lifecycle**
FINDING: For a short-lived, single-use probe grant, a full heartbeat model (like `DutyLeaseCoordinator`) is unnecessary overhead. The pattern that fits best is a fixed-timeout single-flight lease.

RESOLUTION: The `RecoveryProbeGrant` will move through the following concrete state transitions:
1. `GRANTED`: Created with a fixed expiration timestamp (e.g., `now + 5_minutes`). This serves as the single-flight lease for the circuit.
2. `CLAIMED`: A worker atomically CAS-updates the grant to `CLAIMED` when starting the probe.
3. `SUCCEEDED` / `FAILED`: The worker applies the probe result, consuming the grant permanently and updating the circuit state.
4. `EXPIRED`: If a worker crashes between `GRANTED`/`CLAIMED` and execution, the expiration timestamp will elapse. A new grant cannot be issued while an unexpired one exists, preventing parallel probe spam. Once expired, the grant is considered exhausted (failing closed) and the circuit remains quarantined. The operator must request a new authorization (spending another budget slot) to retry. This provides safe partial-failure recovery without requiring resume mechanisms.

Successful vote first prints `[HUB] PROPOSAL-VOTE {round_id} | {voter}:{choice.upper()}` and, only when the coordinator committed an outcome, one exact second line: `[HUB] PROPOSAL CONSENSUS_OK {round_id} | unanimous agree: {agreed}`, `[HUB] PROPOSAL NACK {round_id} | disagreed: {disagreed}`, `[HUB] PROPOSAL ESCALATED {round_id} | N < 2 (human_gate)`, `[HUB] PROPOSAL ESCALATED {round_id} | mid-round gate closure (human_gate)`, or `[HUB] PROPOSAL ESCALATED {round_id} | proposer self-finalization blocked (human_gate)`. These ordering/normalization requirements come directly from ledger lines 161 and 181; they are not separate compatibility-owned state transitions.

**2. Vote vocabulary and outcome ladder -- extend the domain, do not alias away information**

Recommendation: extend `ConsensusService.cast_vote()` to accept exactly `agree`, `disagree`, `abstain`, and `need_more_info`, and add optional reason preservation. Do not translate `ABSTAIN` or `NEED_MORE_INFO` into `disagree`, a final-call ACK, or an escalation request: each would destroy a real legacy vote fact. The gap-2 ratified design already specifies ordinary abstention as a non-agreement (`HUB-REPLACEMENT-GAP2-CONSENSUS-2026-08-24.md:61-70,94-105`); `need_more_info` is the one legacy-specific addition.

Resolution accounting must change with the vocabulary, not merely widen the validation set at `peerhub/governance/consensus.py:339-367`:

- Persist all four choices in `votes[actor_id]`; a new pre-terminal vote from that actor supersedes the visible choice exactly as current correction behavior does.
- Add/derive `recorded_votes = len(votes)` for participation observability and `decisive_votes` for the `agree`/`disagree` facts. Define existing `quorum.counted_votes` as the number of required-participant `AGREE` votes, and set `quorum.reached` only when that count meets `required_votes` and no stored eligible vote is `DISAGREE`. `ABSTAIN` and `NEED_MORE_INFO` do **not** count toward `required_votes`, do not satisfy quorum, and do not themselves produce NACK. They keep the round open and may be superseded before a terminal outcome. Counting them would let `agree + abstain` satisfy a two-voter quorum, close voting, and potentially approve without unanimity -- the opposite of legacy semantics.
- `DISAGREE` is a recorded decisive veto but never counts toward approval quorum. Because current `cast_vote()` moves to `quorum_reached` based on raw vote count and current `resolve()` cannot immediately resolve a pre-quorum dissent (`peerhub/governance/consensus.py:264-297,320-380`), add a narrow consensus-domain `reject_on_dissent()` transition (or an equivalently strict branch in `resolve()`) that verifies a stored eligible `disagree` and writes terminal native outcome `rejected`. The compatibility presenter renders that outcome as legacy `NACK`. Do not fake the prerequisite by requesting and immediately self-resolving a human escalation.
- Unanimous `AGREE` across the frozen required tuple, with at least one agreeing voter other than the proposer, reaches quorum and calls existing `resolve(..., outcome="approved", basis="legacy proposal unanimous agree")`; compatibility renders `CONSENSUS_OK`.
- The three human-gate cases -- fewer than two snapshotted voters, a snapshotted voter whose native gate closes mid-round, and completed participation in which the proposer is the only agreeing voter -- call the existing `request_escalation(round_id, reason, requester_id, tier=0, required_authority="human-tier-0")`. That method already records reason/requester/tier/deadline/authority while leaving the round open for a real authority (`peerhub/governance/consensus.py:217-244`). Compatibility renders `ESCALATED`; it must not mislabel the round as terminally resolved.
- With pending voters, or only non-decisive `ABSTAIN`/`NEED_MORE_INFO` facts and no completed self-only condition, no outcome line is synthesized and the round remains open. A later correction or the existing timeout/escalation path may advance it.

This is a narrow but real change to the shipped consensus schema and tests, not compatibility-only wiring. It also exposes an existing generic mismatch that implementation must address carefully: today `agree + disagree` reaches raw-count quorum (`tests/integration/governance/test_consensus.py:53-74`), and final-call completion can write `approved` without inspecting those choices (`peerhub/governance/consensus.py:168-177`). Proposal handling must never inherit that approval path in the presence of dissent.

Vote application remains CAS-governed. Concurrent `proposal-vote` calls may produce a typed `StaleRevisionError`; a retry must re-read and recompute from the winning revision. They can never silently clobber a different voter's vote. The coordinator must expose an idempotent outcome-reconciliation step, invoked after each accepted vote and by pending-round recovery, so a crash after the vote CAS but before the follow-up resolution/escalation does not strand a decisive round. Likewise, concurrent adds either receive different IDs after the bounded allocation retry or surface a conflict; they never overwrite one proposal target. These are deliberate, correct divergences from the two documented unlocked legacy races (`PHASE1-PARITY-LEDGER-BATCH5-2026-08-20.md:163,176,183,196`), not parity gaps.

**3. D-1 invariant write -- bridge, do not write the live document in the vote command**

Decision: preserve the consequential intent through an immutable `ratified-invariant-write-request`, consumed by a separate authenticated human/authority-bearing workflow. Do not port the literal file write and do not waive the behavior entirely.

A literal port would make a vote command edit a live architecture document with no native document authority model; it would couple a durable DB transition to an untransactional filesystem mutation; it would reintroduce `INV-NN` allocation races; and it would risk wrong-workspace paths, symlink/path substitution, malformed table insertion, encoding/newline damage, permission failures, and a split-brain state where consensus says approved but the file write failed (or vice versa). Legacy's tempfile + `os.replace` makes one file replacement crash-atomic, but it cannot make the consensus mutation and file replacement atomic (`PHASE1-PARITY-LEDGER-BATCH5-2026-08-20.md:182-183,195`).

The approved resolution should instead commit a non-noop `EffectIntent(kind="governance.ratified-invariant-write-request", payload=...)` in the same broker transaction as the consensus revision. The broker already commits target CAS, immutable mutation/plan/receipt, and outbox event together (`peerhub/governance/broker.py:311-421`) and exposes restart-safe effect discovery/claim/receipt handling (`peerhub/governance/broker.py:457-617`). The payload snapshot should include deterministic request ID, round ID and approved revision, resolution decision hash, proposer, title/question/body/source hash, frozen participants/votes, proposed invariant text (`Changes`), target-doc hint (`10-invariants.md`, never an unrestricted absolute path), and requested timestamp.

This requires a narrow consensus-domain change because `_submit()` currently hard-codes `EffectIntent(kind="consensus.noop", ...)` (`peerhub/governance/consensus.py:507-533`): approved proposal resolution must be able to supply this typed intent, while every unrelated consensus operation retains the noop default.

A separate idempotent projector must claim that effect and materialize the immutable target `ratified-invariant-write-request:{round_id}:{decision_hash}` with `expected_revision=0`, `kind="ratified-invariant-write-request"`, `scope=round_id`, `schema_version=1`, the complete frozen payload above, and fixed status `REQUESTED`; an existing target is acceptable only if its identity and snapshot match exactly. An operator then either rejects it or invokes a future authority-bearing document-application workflow. Application/rejection evidence must be a separate immutable result record; do not mutate the request or let the compatibility command edit the document. This matches `ArbiterReviewCoordinator`, which creates an immutable `arbiter-review` request before recording a separate opinion (`peerhub/application/arbiter_review.py:496-563,631-707,710-733`), and the `report-error` bridge, which commits its evidence series before creating a distinct `quarantine-review` request (`peerhub/governance/operational_errors.py:102-264`) that `QuarantineReviewCoordinator` later resolves across the governance/health boundary (`peerhub/application/quarantine_review.py:27-151`). The broker outbox is added here because it closes the otherwise-real crash gap between approval and creation of the second record.

**4. Placement**

Place the main workflow in a new `peerhub/application/proposals.py` coordinator. Proposal creation joins a policy voter source, `PeerRegistryService`, `HealthService`, clock/ID allocation, and `ConsensusService`; voting joins consensus mutation, current health re-check, outcome selection, escalation, and the invariant-request bridge. That is application orchestration across multiple domains, exactly like `QuarantineReviewCoordinator` (governance request + peer registry + health) and `ArbiterReviewCoordinator` (broker + consensus + external review execution), not a self-contained governance journal.

Keep only consensus invariants in `peerhub/governance/consensus.py`: the four-value validation/reason field, decisive-vote accounting, and strict reject-on-dissent transition. Put the immutable invariant-request creator/projector in `peerhub/governance/invariant_requests.py`; the eventual filesystem-applying reviewer belongs in `peerhub/application/` because it crosses governance authority and workspace I/O. This follows the explicit placement rationale in `peerhub/governance/feedback.py:1-8`: self-contained journal logic lives under `governance/`, while adapter/health-crossing workflows live under `application/`.

**5. Remaining architecture questions -- do not guess during implementation**

1. **Authoritative voter policy source:** no shipped native object exposes legacy `r10_voters`. `PeerRegistryService.list_nodes()` is inventory, not voting policy. Decide whether to add a versioned governance-electorate provider, import legacy protocol configuration, or require an explicit configured electorate before implementation.
2. **Zero eligible voters and missing health evidence:** `ConsensusService.propose()` rejects an empty required tuple through `_quorum_required()`, while the ledger does not specify the all-unhealthy/empty-voter fixture. This design recommends fail-closed exclusion for a missing health projection and immediate human escalation for one voter, but zero voters requires an explicit choice between rejecting creation and introducing a creatable immediately-escalated round.
3. **Exact self-finalization trigger:** the ledger confirms the outcome but does not state with enough precision whether a proposer-first `AGREE` escalates immediately or only after every other participant has produced a non-agree/non-pending response. The recommendation above uses completed participation to avoid prematurely closing an otherwise normal round; verify against the real legacy branch before TDD fixtures are frozen.
4. **Invariant request consumer authority and document contract:** the immutable request bridge is ratified here, but PeerHub has no authority-bearing architecture-document writer, target-doc allowlist, invariant-table parser, or CAS allocator for `INV-NN`. Those require a separate design/TDD round. Until it exists, approved proposals correctly remain pending write rather than silently mutating files.
5. **Effect-projector execution:** the projector and immutable request-target shape are decided above, but no generic background effect executor is wired for this new kind. A later design must choose whether an explicit operator command or a bounded worker invokes the projector; either host must use the broker claim/receipt protocol and recover claimed-but-unreceipted work.
6. **Risk vocabulary:** the current service stores arbitrary risk and does not use it in quorum math. The `med -> normal` compatibility normalization above is concrete for this bridge, but a future typed risk policy must ratify its vocabulary before changing historical meaning or final-call requirements.

### Broker submit/drain/status scouting verdict (2026-09-02): generic mutation queue waived; bounded effect-outbox status is a real read-only quick win

Research-only review against the complete Parity Ledger entries (`docs/design/PHASE1-PARITY-LEDGER-BATCH5-2026-08-20.md:218-273`), the complete shipped broker, its SQLite unit of work/repository, and representative room, consensus, and peer-registry service callers. No compatibility or service code is authorized by this section.

**1. `broker-submit` / `broker-drain` verdict -- WAIVE AS ARCHITECTURALLY INCOMPATIBLE, not a missing PeerHub queue.** Legacy `broker-submit` validates a filename from a fixed raw-file allowlist, parses one arbitrary JSON value, captures the file's SHA-256 (or `"ABSENT"`), and atomically writes a request file without changing the target (`PHASE1-PARITY-LEDGER-BATCH5-2026-08-20.md:218-234`). Only `broker-drain`, under its filesystem lock, checks that hash, replaces the whole JSON file, and moves the request to `done/` or `error/` (`ibid.:237-253`). The separation is load-bearing legacy behavior: submit alone is not apply.

PeerHub deliberately closes that gap inside one call. `GovernanceBroker.submit(request: MutationRequest) -> MutationSubmission` reads the idempotency binding and current target, validates the integer revision, builds the plan/receipt/effect, CAS-writes the target, persists the immutable request/plan/receipt/binding/outbox event, and commits once (`peerhub/governance/broker.py:311-421`). The production unit of work is one `BEGIN IMMEDIATE` SQLite transaction with rollback-on-exit and one complete commit (`peerhub/persistence/sqlite.py:752-853`); the target update itself is guarded by `WHERE target_id = ? AND revision = ?` (`peerhub/persistence/sqlite_governance.py:93-148`). Thus the *composed successful effect* of legacy submit followed by drain is already represented by one domain-service call that constructs a `MutationRequest` and ends in `GovernanceBroker.submit()`. The two legacy actions cannot be mapped individually: calling native `submit()` from `broker-submit` would apply too early, while preserving `broker-drain` would recreate a redundant pre-commit queue solely to retain the old command boundary.

The raw-payload mismatch independently makes a generic alias unsafe. `MutationRequest.desired_state` is only frozen as a JSON mapping (`peerhub/governance/contract.py:145-198`), and `plan_mutation()` installs it as the complete next target state (`peerhub/governance/mutations.py:83-132`); the broker core is CAS/idempotency/effect machinery, not a per-domain schema validator. Real callers construct narrow records and enforce their own invariants: rooms and threads have separate target states and relationship checks (`peerhub/governance/rooms.py:128-202,227-272`), consensus creates one typed round with frozen participant/quorum/vote fields (`peerhub/governance/consensus.py:43-111`), and node registration validates adapter/profile identity before writing `peer-node:{node_id}` (`peerhub/application/peer_registry.py:89-138`). Target IDs are not uniformly prefixed -- rooms and consensus rounds currently use their caller-supplied IDs while peer nodes use `peer-node:{node_id}` -- but they are still individually keyed, typed domain records rather than one `state.json`, `nodes.json`, or `consensus/{round}.json` aggregate.

Consequently, translating a filename plus arbitrary JSON directly into `GovernanceBroker.submit()` would let the caller replace a target state without the corresponding service's validation. Translating one legacy aggregate honestly would instead require a schema-aware importer that diffs and fans out to multiple domain commands, defines partial-failure/atomicity rules across multiple targets, and rejects payloads the legacy contract accepts. That is a different migration product, not `broker-submit` parity. There is no honest narrower generic-write interpretation. Do not add pending/done/error tables or files, and do not expose the low-level broker as an arbitrary JSON write API. **Confidence: very high (0.99).**

**2. `broker-status` verdict -- KEEP AS A SMALL STANDALONE NATIVE QUICK WIN, but explicitly redefine it as bounded unfinished-effect status.** Literal legacy parity is impossible and should be waived: legacy counts pre-apply mutation request files plus historical `done/error` files (`PHASE1-PARITY-LEDGER-BATCH5-2026-08-20.md:256-272`), whereas PeerHub's outbox is committed atomically with the target transition, represents post-transition effect delivery, and has `PENDING -> CLAIMED -> CONSUMED` delivery state plus an immutable success/failure receipt (`peerhub/governance/contract.py:34-53,381-405,530-567`). It must not print those as if they were the same lifecycle.

There is nevertheless an honest replacement for the operator intent “what broker-owned work remains?”: `GovernanceBroker.recover_pending_effects(*, limit: int = 100) -> tuple[PendingEffect, ...]` is a pure read and returns committed, unreceipted governance effect deliveries in outbox order (`peerhub/governance/broker.py:457-502`). Each `PendingEffect` carries the event, its transition receipt, and `READY_TO_CLAIM` or `CONFIRMATION_REQUIRED` disposition (`peerhub/governance/contract.py:587-615`); the SQLite query deliberately includes both unclaimed `PENDING` and claimed-but-unreceipted `CLAIMED` deliveries (`peerhub/persistence/sqlite_governance.py:531-566`). `get_outbox_event(event_id)` and `get_effect_receipt(event_id)` provide read-only point drill-down (`peerhub/governance/broker.py:439-455`). `claim_effect()` and `record_effect_result()` are mutating worker operations and are not part of status.

The exact narrow scope is one read-only application/CLI result, preferably named `governance.effect.status` rather than the catalog's current misleading `governance.mutation.status` label (`peerhub/application/legacy.py:230-232`). Call `recover_pending_effects(limit=21)`, return/list the first 20 in stable outbox order with `event_id`, `OutboxState`, recovery disposition, effect kind, target ID, and target revision, and set `has_more` from the twenty-first item. Report `visible_unfinished_count` (and counts by visible state/disposition), not an exact global total: the public method is bounded and exposes no cursor/count operation. Do not synthesize legacy `done` or `error` totals. If an exact total later becomes a requirement, add a separately reviewed count/pagination read; do not infer it from a truncated page. This is descriptor/translation/presentation work over a shipped read surface, not a new queue or drain worker. **Confidence: high (0.94) that this bounded native status is useful and honest; very high (0.99) that it is not literal legacy queue parity.**

**3. Effect on the prior backlog flag.** This confirms the earlier one-line diagnosis at line 564 for the write lifecycle and turns it into a firm waiver: `broker-submit`/`broker-drain` are false friends, not “real gap, needs infrastructure.” It narrows one part of that bundled rejection: `broker-status` does have a real standalone native equivalent when it is presented truthfully as unfinished post-commit effect delivery status. Therefore the prior flag is **confirmed for submit/drain and revised only for status**. **Confidence: very high (0.98).**
