## `arbiter-review` RATIFIED (2026-08-28): reuses existing dispatch machinery, one normal-sized round, not a new-infrastructure project

Real legacy behavior (`docs/design/PHASE1-PARITY-LEDGER-BATCH5-2026-08-20.md` §16): requires an existing consensus round; checks arbiter config (disabled -> `{"fired": false, "reason": "arbiter_disabled"}`, no side effects); detects dissent; checks a rolling 5-hour budget window (max 5/5h, exceeded -> `{"fired": false, "reason": "budget_exceeded"}`, no side effects); if it fires, invokes the configured arbiter model, appends a `FINAL_OPINION`, records the budget consumption. Not idempotent when it fires.

**Overturned assessment**: the earlier ratification concluded this needs genuinely new subprocess/`ProcessSupervisor`-class infrastructure. Direct verification found legacy's "isolated subprocess" is conceptually `hub.py ask --to <arbiter>` -- i.e. exactly what peerhub's own already-built, already-proven `execute_direct_ask()` (`peerhub/application/direct_ask.py`) does: resolves a peer/profile, live readiness probe, capability/routing admission, real adapter/`ProcessSupervisor` dispatch, verified response, synchronous. `AuthenticatedSubject` is plain immutable principal/evidence data, not inherently interactive -- `ApplicationAPI` already constructs one from a `RequestContext` for other dispatch admission. **No new process-invocation infrastructure is needed.**

**Real corrections found during verification** (ratified, cite these instead of the parity ledger's shorthand where they conflict):
- Legacy's "rolling" budget is an ANCHORED 5-hour window (`{window_start, count}`, resets 5h after the FIRST counted invocation in the window), not a continuously sliding list of the last 5 timestamps.
- Real legacy source returns `budget_exhausted`; the parity ledger doc (and this ratification's own compat contract) says `budget_exceeded`. Ratified: implement `budget_exceeded` (the already-published compat value), pin it in a test, note the discrepancy rather than silently picking one.
- Dissent includes BOTH explicit non-agree votes AND required voters with no vote at all (`no_vote`) -- not just explicit disagree.
- **Scope boundary, ratified as non-negotiable**: manual `arbiter-review` records a `FINAL_OPINION` only -- it does NOT itself apply an override to the consensus outcome. Override application is a separate, NOT-yet-built auto-finalization path. Do not smuggle automatic consensus-outcome mutation into this round.
- Real legacy triggers on `dissent`/`r10_final`; peerhub's current consensus round schema has no `r10_final` marker -- do not fabricate one, `dissent` alone is real and sufficient for this round.

**One real remaining prerequisite decision, ratified**: legacy's configured arbiter is `cc.fable` (`--model claude-fable-5 --effort high`), which is NOT currently a dispatchable peerhub profile (the Claude adapter only accepts `cc.standard`). Per this session's own memory record (`reference_cc_fable_profile_broken_2026_08_19` -- `cc.fable` is a KNOWN-BROKEN profile in this real environment since ~2026-07-17, fails every real dispatch and cascades cc health to RED, independent of whether peerhub configures it), configuring `cc.fable` as peerhub's arbiter would fail in practice even if wired. **Ratified: use a real, currently-working high-capability profile as the default configured arbiter instead** (`cc.deepthink` or `cc.effort` -- both proven working throughout this session's own dispatches), documented as a deliberate substitution for a literally-broken legacy default, not a silent behavior change -- matches this session's established "superset-compat, real capability over a broken literal match" precedent.

### `peer-registry` RATIFIED (2026-08-28): critique round (cc.deepthink) overturns cx's singleton, resolves the adapter-kind-safety question

Independent critique of cx's research above, per this session's standing research-then-critique discipline. Four of cc's citations independently spot-checked by the terminal directly against source (`InvocationPlan`'s docstring word-for-word, the three real adapters' single declared `ProfileDescriptor.profile_id` each, `resolve_peer_target`'s `ProfileNotFoundError` on an unmatched `profile_id`, `create_room`'s `expected_revision=0` CAS pattern) -- all checked out exactly as cited. hub.py itself was intermittently broken by an unrelated stalled Engram merge at the P:\ root sandbox during this round (unrelated to peerhub, fixed by the user's `git merge --abort`, see session notes) -- this critique dispatch is what confirmed the fix worked.

**Adapter-kind-safety question, resolved: reference an already-registered adapter kind + `profile_id`. No generic-command concept.** Traced legacy's real behavior end to end in `hub.py`/`hub_peer.py`: `register-node` writes only to `nodes.json`; `_load_nodes()` drops any custom node whose id collides with orchestration's `hub_nodes`/`retired`; dispatch gates on `is_routable()`, which returns `False` for exactly the set a custom node can occupy. So legacy's own `invoke`/`invoke_args`/`memory`/`timeout` fields are **write-only** in the shipped system -- never read by dispatch, `peer-status`'s live probe, or anywhere else (confirmed by grep). A "constrained generic-command" concept would be a net-new arbitrary-command-execution primitive legacy itself doesn't have, and has no seam in peerhub: `InvocationPlan.argv` is "mechanically generated from a resolved `PeerProfileBinding` + `AdapterRequest` … never independently specified by a caller" (peerhub/adapters/contract.py docstring, verified). Field disposition: `invoke` is **re-typed** into `peer_kind` via the existing `_CLI_ALIASES` vocabulary (`claude`/`codex`/`agy` -> `cc`/`cx`/`ag`) rather than dropped, since legacy's own `get_adapter()` already treats it as an adapter-kind selector, not a literal command; `invoke_args`/`memory`/`timeout` are rejected fail-closed (explicit error, not silently accepted-and-discarded) -- matching a real prior house precedent of failing closed on invented Claude-style `invoke_args`/`memory` defaults (`_sys/ai/backlog.json:568`); `tier` is stored display-only, explicitly with no authority (native capability grants are per-dispatch via `CapabilityGrantDecision`, never registry config); `node_type` is stored as validated free text (matching the existing `ArtifactSpec.access_mode`/`lifecycle` house pattern of not inventing an enum vocabulary), with `"virtual"` rejected since peerhub has no such adapter.

**Schema, corrected from cx's singleton sketch: one `peer-node:{node_id}` target per node, not a `peer-registry:workspace` singleton.** Two reasons: the parity ledger's own comparator for `list-nodes` says ordering is explicitly NORMALIZED/out of contract, so `node_order` isn't needed (`list_targets` already gives deterministic `ORDER BY target_id`); and a singleton is the minority pattern in this codebase (5 of 6 broker domains use per-entity targets) reserved for genuine cross-entity invariants like `arbiter-budget:workspace`'s shared count/window -- node registration has no such invariant, so a singleton would force an unnecessary CAS-retry loop and make `list_targets` unusable. State: `kind: "peer-node"`, `scope: None`, `schema_version: 1`, `node_id`, `peer_kind`, `profile_id`, `adapter_version` (snapshotted at bind time), `tier`, `node_type`, `registered_at`, `registered_by`, `updated_at` -- deliberately omitting `invoke`/`invoke_args`/`memory`/`timeout`/`node_order`. `list_nodes()` must union derived base rows for the `_CLI_ALIASES` roots (`cc`/`ag`/`cx`, matching the ledger's own "3 configured nodes" positive fixture) with registered rows, base winning on collision -- the faithful port of legacy's `{**custom, **base}` merge with `configured` taking precedence; `register_node` rejects a `node_id` colliding with a base adapter/alias rather than silently allowing a shadowed row.

**Placement:** `peerhub/application/peer_registry.py` (not `governance/`) -- validating `peer_kind`/`profile_id` needs `peerhub.adapters.registry`, which would pull real adapter implementations into the governance layer; `ArbiterReviewCoordinator` is the precedent for an application-layer service owning a governance target.

**CAS/idempotency, corrected from cx's sketch:** verified uniform across five real domains (rooms/lessons/tasks/consensus/arbiter_review) -- every service mints a fresh `request_id` per call as the idempotency key, making the broker's deterministic-idempotency-key path structurally unreachable; all real concurrency safety is `expected_revision` CAS (`0` on create, `current.revision` on read-modify-write). Do not invent a deterministic key for peer-registry -- that would make a *differing* re-registration raise `IdempotencyPayloadMismatchError`, contradicting legacy's actual semantics, which is a blind upsert (identical re-registration is a no-op only as a side effect of writing the same bytes back; a *differing* one silently overwrites). "No-op" should mean **state-stable re-submission** (matching `mark_read`'s real precedent: revision still increments, only the visible state stays byte-identical), not "no write happens at all." `duty_lease.create_lease`'s reject-on-conflict semantics are NOT valid precedent here -- it isn't even a `TargetState`/broker domain, and its behavior is backwards from legacy's upsert model.

**One real bug found and fixed in passing, unrelated to peer-registry:** `arbiter_review.py`'s `_DEFAULT_PROFILE_ID` was `"cc.deepthink"`, which does not exist as a declared profile on the real Claude adapter (only `"cc.standard"` is declared) -- every enabled arbiter review would have failed with `ProfileNotFoundError`, latent only because the arbiter ships disabled by default. Fixed same-day (commit `1879970`), independently reproduced and verified (full suite 1151 passed, 0 new pyright errors).

**Two items recorded, neither blocking implementation:** the `fix-register-node-pos-01` ledger fixture (`--invoke python`) is now a stated, deliberate parity break (rejected rather than accepted) and should be annotated in the ledger as a deviation, not left to be discovered as a future test failure; `telemetry/presenter.py` independently uses `cx.deepthink`/`ag.deepthink` display-profile names that also don't match any real declared `ProfileDescriptor.profile_id` -- flagged as a separate, not-yet-investigated question (is the telemetry dashboard's profile vocabulary supposed to diverge from the adapter registry's, or is this the same class of bug as the arbiter default -- undetermined, needs its own look before assuming either way).

**Ready to hand to an implementation round.** Service signatures ratified: `PeerRegistryService.__init__(broker, *, clock, ids)`, `register_node(*, node_id, peer_kind, profile_id=None, tier=4, node_type="agent", actor_id) -> MutationSubmission`, `get_node(node_id) -> TargetState`, `list_nodes() -> Sequence[TargetState]`.

**Update (2026-08-29): DONE, exactly as ratified above.** See the "Where things stand right now" section at the top of this doc for the implementation round's summary. `register-node`/`list-nodes` now translate and execute end-to-end (39/90).
