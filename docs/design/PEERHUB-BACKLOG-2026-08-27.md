### `LeadershipService` RATIFIED (2026-08-30): a real workspace-global singleton, deliberately NOT built on DutyLeaseCoordinator

Research (cx.deepthink) then critique (cc.deepthink), both independently spot-checked by the terminal directly against real `_sys/core/hub.py` source -- every checked claim, including two genuinely counterintuitive ones, confirmed accurate: **an unexpired `challenge_until` window PERMITS a competing claim to overwrite the pending claimant -- it does NOT protect the incumbent** (health-gating only protects a leader once the window has expired or never existed; the opposite of the natural-sounding assumption); and **`DutyLeaseCoordinator`'s existing AP-20-style guard has a genuine off-by-one vs. real legacy** (rejects the 3rd same-peer claim; legacy allows claims 1-3 and rejects the 4th) -- separate confirming evidence, not a bug to fix in `duty_lease.py` itself, that `LeadershipService` must not reuse that machinery.

**Placement: `peerhub/application/leadership.py`, NOT built on `DutyLeaseCoordinator` at all.** Confirmed incompatible on every axis: room-scoped vs. legacy's workspace-global; immediately-`ACTIVE` vs. legacy's `PENDING`-with-challenge-window; heartbeat-expiring vs. legacy's non-expiring; fence-strict-yield-rejection vs. legacy's warn-and-vacate-for-anyone. The currently-shipped `routing.leadership.claim`/`.yield` (the bug this replaces) are exactly this wrong reuse.

**Schema: one singleton `leadership:workspace` target** (matching `arbiter-budget:workspace`'s precedent for when a singleton is justified -- a genuine workspace-wide at-most-one-leader invariant, and AP-20's check-then-append must be atomic with the leadership write in one `broker.submit()`). State: `status` (`VACANT|PENDING|ACTIVE` -- `ACTIVE` is reserved vocabulary this round, nothing in this round's scope ever writes it, see below), `term` (native-only audit convenience, explicitly non-authoritative, nothing may gate on it), `claim_id` (fresh every successful claim), `leader` (null, or `{peer_node_id, peer_node_target_id, peer_node_revision, peer_kind, profile_id, adapter_version}` -- a frozen registry binding, requiring `peer_registry.get_node()` to resolve; unregistered-text leaders are rejected, closing a real legacy pathology where an unresolvable agent name becomes permanently unchallengeable since it always reads as health `UNKNOWN`), `claimed_at`, `claimed_by`, `challenge_until`, `domain`, `reason` (both with legacy's exact fallbacks: `domain = domain or reason or "general"`, `reason = reason or "manual_claim"`), `claim_basis` (null, or `{disposition: VACANT_CLAIM|SELF_RECLAIM|OPEN_WINDOW_CHALLENGE|FAILED_INCUMBENT_TAKEOVER, incumbent_peer_node_id, projection_id, projection_revision, availability_state, admission_state, stale_at_read}`), `yielded_by`, `yielded_at`, `yield_reason`, `coordinator_history` (embedded, bounded to last 10, matching legacy's own `history[-10:]`), `updated_at`.

**Claim predicate** (re-evaluated fresh on every CAS retry): AP-20 first, unconditionally (applies even to a self-reclaim, matching source ordering) -- reject iff the last `threshold` history entries all belong to the candidate. Then: `VACANT`/absent -> `VACANT_CLAIM`; candidate equals current leader -> `SELF_RECLAIM`, no incumbent health check; `challenge_until is not None and now < challenge_until` (gated purely on the timestamp, no `status` condition -- a narrowing cx's draft had that critique removed) -> `OPEN_WINDOW_CHALLENGE`, unconditional; otherwise evaluate the *incumbent's* health via `HealthService.get_health_projection()` on its stored `peer_kind`/`profile_id` -- replaceable (`FAILED_INCUMBENT_TAKEOVER`) only if a projection exists AND (availability in `{UNAVAILABLE,STALE}` OR admission in `{QUARANTINED,COOLDOWN,RECOVERY_REQUIRED}` OR stale past `readiness_freshness_seconds`); otherwise raise `LeadershipIncumbentProtectedError` -- absent evidence protects the incumbent (the mirror image of role-assignment's fail-open-admits-a-candidate polarity: same deny-list shape, opposite user-visible outcome, since this gates an incumbent rather than admitting a candidate). The new candidate itself is never health-gated -- legacy only ever gates the incumbent.

**Yield**: always mutates (even already-`VACANT`, no target, or a non-leader yielding -- returns `owner_mismatch`/`previous_leader_peer_node_id` as warning metadata, never raises). Legacy fully *replaces* the `leadership` sub-object rather than partially updating it, so yield must null `leader`/`claim_id`/`challenge_until`/`claimed_at`/`claimed_by`/`domain`/`claim_basis`, not just set `status=VACANT` -- retaining a stale `challenge_until` after a yield (cx's original draft) would leave actively misleading residue. `term` and `coordinator_history` are retained (legacy siblings of `leadership` in `state.json`, untouched by yield).

**No `activate_pending_leadership()` this round** -- decisive new evidence found in critique: grepping every real legacy write of `leadership.status = "ACTIVE"` found exactly one call site, and it belongs to `action_terminal_handoff`, a *different* action in a domain peerhub already has (`TerminalDutyService`) -- not a timeout-driven settle step. Nothing in legacy ever transitions `PENDING` to `ACTIVE` on elapsed time; there is no legacy sweep/settle/activate operation at all. Building one now would be an invented state transition with no legacy counterpart and no caller. The `ACTIVE` <- `terminal-handoff` cross-domain coupling is recorded as a real, separate scoping question for later, not designed now.

**Retry**: bounded 16-attempt CAS loop (mirroring `ArbiterBudgetManager`), full predicate re-evaluated fresh each attempt -- justified because legacy serializes these operations under one real global lock, making CAS-retry-with-fresh-reevaluation the correct analog of sequential processing (a second concurrent claim genuinely should see the first's new `PENDING` state and be able to challenge it within the window), not a shortcut. Only `StaleRevisionError` may consume a retry attempt -- AP-20 and incumbent-protection rejections raise immediately, so a losing claimant doesn't burn 16 attempts re-deriving the same refusal. Yield's warning metadata must be computed from the winning attempt's read, not a stale earlier one.

**Errors**: two distinct types, both subclassing `InvalidMutationError` (matching `RoleAssigneeUnavailableError`'s precedent) -- `LeadershipMonopolyError` (`ErrorCode.ACTOR_UNAUTHORIZED`, the actor is specifically barred) and `LeadershipIncumbentProtectedError` (default `INVALID_PARAMS`; `PEER_UNAVAILABLE` would be the wrong code here since the incumbent IS available -- that's precisely why the claim fails).

**Policy**: `LeadershipPolicy(challenge_window_seconds=60, monopoly_threshold=3, history_limit=10)` injected with hardcoded defaults, validated in `__post_init__` like `FinalArbiterPolicy`. No new `.peerhub/leadership.json` this round -- `arbiter.json`'s file-presence-as-enablement-switch pattern doesn't transfer (leadership has no on/off semantics, just tuning constants legacy itself reads from the *shared* protocol config, never a leadership-specific file), and inventing a third bespoke config loader would pre-empt the still-open "Configuration/telemetry scouting" cluster's own eventual decision.

**Deferred, recorded but explicitly out of scope this round**: pressure-reason task checkpointing on yield (`_checkpoint_active_tasks`, would drag `TaskService` into the constructor for an effect legacy performs outside its state lock, no bearing on leadership correctness); the AP-20-violation host runtime-directive write (same class as the already-flagged `directive-add/list/clear` host-level cluster); a legacy normalization sweep that vacates leadership when the leader is no longer a routable root peer (no peerhub counterpart yet).

**`elect-leader` remains separately blocked**, unlocked but not solved by this round: it needs `claim_leadership(..., domain=...)` as its landing seam (confirmed a clean fit) but ALSO needs real capability-matching scoring (`_matching_peers(needs, effort)`) that peerhub still lacks entirely -- `RoutingService.select_route()` only does boolean eligibility with equal weights, not scored matching. Separate prerequisite, separate round.

2. **The 16-attempt CAS retry loop, kept -- but as an explicitly justified exception, not a default.** `operational-error-series` is a genuine shared-counter aggregate multiple callers can legitimately race to append to (like `arbiter-budget:workspace`), unlike `role_assignment`/`feedback`/`peer_registry`'s per-entity domains, which deliberately do NOT retry because retrying could silently act on stale ownership/assignment facts. 5. **One new bug ag's design didn't catch, found by cx:** creating the review-request *before* the series CAS wins could leave a durable review record referencing a report that never actually committed (if the series CAS then fails and exhausts retries). Corrected sequencing: the review-request is only created *after* the series CAS has already succeeded.

Ratified `OperationalErrorService(broker, *, clock, ids)` with `report_error(*, peer_key, pattern, severity, detail, actor_id, threshold=3) -> MutationSubmission`. `threshold` is pinned per-series on first creation; a later call supplying a different threshold for the same series is rejected rather than silently changing escalation policy mid-series. ### `peer-registry` RATIFIED (2026-08-28): critique round (cc.deepthink) overturns cx's singleton, resolves the adapter-kind-safety question

Independent critique of cx's research above, per this session's standing research-then-critique discipline. Four of cc's citations independently spot-checked by the terminal directly against source (`InvocationPlan`'s docstring word-for-word, the three real adapters' single declared `ProfileDescriptor.profile_id` each, `resolve_peer_target`'s `ProfileNotFoundError` on an unmatched `profile_id`, `create_room`'s `expected_revision=0` CAS pattern) -- all checked out exactly as cited. hub.py itself was intermittently broken by an unrelated stalled Engram merge at the P:\ root sandbox during this round (unrelated to peerhub, fixed by the user's `git merge --abort`, see session notes) -- this critique dispatch is what confirmed the fix worked.

**Adapter-kind-safety question, resolved: reference an already-registered adapter kind + `profile_id`. No generic-command concept.** Traced legacy's real behavior end to end in `hub.py`/`hub_peer.py`: `register-node` writes only to `nodes.json`; `_load_nodes()` drops any custom node whose id collides with orchestration's `hub_nodes`/`retired`; dispatch gates on `is_routable()`, which returns `False` for exactly the set a custom node can occupy. So legacy's own `invoke`/`invoke_args`/`memory`/`timeout` fields are **write-only** in the shipped system -- never read by dispatch, `peer-status`'s live probe, or anywhere else (confirmed by grep). A "constrained generic-command" concept would be a net-new arbitrary-command-execution primitive legacy itself doesn't have, and has no seam in peerhub: `InvocationPlan.argv` is "mechanically generated from a resolved `PeerProfileBinding` + `AdapterRequest` … never independently specified by a caller" (peerhub/adapters/contract.py docstring, verified). Field disposition: `invoke` is **re-typed** into `peer_kind` via the existing `_CLI_ALIASES` vocabulary (`claude`/`codex`/`agy` -> `cc`/`cx`/`ag`) rather than dropped, since legacy's own `get_adapter()` already treats it as an adapter-kind selector, not a literal command; `invoke_args`/`memory`/`timeout` are rejected fail-closed (explicit error, not silently accepted-and-discarded) -- matching a real prior house precedent of failing closed on invented Claude-style `invoke_args`/`memory` defaults (`_sys/ai/backlog.json:568`); `tier` is stored display-only, explicitly with no authority (native capability grants are per-dispatch via `CapabilityGrantDecision`, never registry config); `node_type` is stored as validated free text (matching the existing `ArtifactSpec.access_mode`/`lifecycle` house pattern of not inventing an enum vocabulary), with `"virtual"` rejected since peerhub has no such adapter.

**Schema, corrected from cx's singleton sketch: one `peer-node:{node_id}` target per node, not a `peer-registry:workspace` singleton.** Two reasons: the parity ledger's own comparator for `list-nodes` says ordering is explicitly NORMALIZED/out of contract, so `node_order` isn't needed (`list_targets` already gives deterministic `ORDER BY target_id`); and a singleton is the minority pattern in this codebase (5 of 6 broker domains use per-entity targets) reserved for genuine cross-entity invariants like `arbiter-budget:workspace`'s shared count/window -- node registration has no such invariant, so a singleton would force an unnecessary CAS-retry loop and make `list_targets` unusable. State: `kind: "peer-node"`, `scope: None`, `schema_version: 1`, `node_id`, `peer_kind`, `profile_id`, `adapter_version` (snapshotted at bind time), `tier`, `node_type`, `registered_at`, `registered_by`, `updated_at` -- deliberately omitting `invoke`/`invoke_args`/`memory`/`timeout`/`node_order`. `list_nodes()` must union derived base rows for the `_CLI_ALIASES` roots (`cc`/`ag`/`cx`, matching the ledger's own "3 configured nodes" positive fixture) with registered rows, base winning on collision -- the faithful port of legacy's `{**custom, **base}` merge with `configured` taking precedence; `register_node` rejects a `node_id` colliding with a base adapter/alias rather than silently allowing a shadowed row.

**Placement:** `peerhub/application/peer_registry.py` (not `governance/`) -- validating `peer_kind`/`profile_id` needs `peerhub.adapters.registry`, which would pull real adapter implementations into the governance layer; `ArbiterReviewCoordinator` is the precedent for an application-layer service owning a governance target.

**CAS/idempotency, corrected from cx's sketch:** verified uniform across five real domains (rooms/lessons/tasks/consensus/arbiter_review) -- every service mints a fresh `request_id` per call as the idempotency key, making the broker's deterministic-idempotency-key path structurally unreachable; all real concurrency safety is `expected_revision` CAS (`0` on create, `current.revision` on read-modify-write). Do not invent a deterministic key for peer-registry -- that would make a *differing* re-registration raise `IdempotencyPayloadMismatchError`, contradicting legacy's actual semantics, which is a blind upsert (identical re-registration is a no-op only as a side effect of writing the same bytes back; a *differing* one silently overwrites). "No-op" should mean **state-stable re-submission** (matching `mark_read`'s real precedent: revision still increments, only the visible state stays byte-identical), not "no write happens at all." `duty_lease.create_lease`'s reject-on-conflict semantics are NOT valid precedent here -- it isn't even a `TargetState`/broker domain, and its behavior is backwards from legacy's upsert model.

Peerhub already has a robust, coordinated, consensus-governed mechanism for prompt injection: **Lessons** (`lessons-propose`, `lesson-inject`, backed by SQLite `command_ledger`). Replacing `runtime-directives` within peerhub would redundantly recreate lessons. These remain local host-tooling actions.
- `credit-status`, `credit-consume`: These interact with `CodexAccountClient` to read and irreversibly consume proprietary "rate-limit reset credits" on an upstream service API (`docs/design/PHASE1-PARITY-LEDGER-BATCH5-2026-08-20.md`, lines 313-350). While peerhub *observes* quotas (via read-only polling in `telemetry/quota_polling.py` to inform `RoutingService`), actively *redeeming upstream account billing/quota tokens* is a highly peer-specific proprietary host integration. Peerhub coordinates peers; if a peer's quota is exhausted, peerhub routes around it. Redeeming a token to wake the peer up is an upstream account management action, not a peer coordination concept.
