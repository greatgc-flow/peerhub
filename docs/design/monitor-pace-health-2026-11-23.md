## C1 One shared calculation
Purpose: the monitor (both modes) and `diag --plan` (text and JSON) must never disagree, and every threshold must have one owner. Evidence: F1 to F4 show today's views derive their words, colours and columns separately (compact `ok/fast`, expand `ON_PACE/THREAT`, diag `spend/hold/rest`). Reason: two pure helpers at extension level (no CLI import) beat per-view logic because tests then pin one function and the docs derive from named constants; a new store or a config layer was rejected as unnecessary.
Decision:
(a) `pool_health(reading, parent_reading, frame_time)` returns per pool, with ALL parent-limit derivation done here (M1, M3, M4 and the plan only format its output): `state` (the existing documented words and precedence n/a ? reset out low fast aged ok, plus `blocked` for a child with positive quota whose fresh limiting parent is out; a stale zero whose reset has passed is `reset`, `aged` only while the reset is pending or unknown); `pace_band` (spend when PACE <= -10, rest when PACE > +20, else ok, on the UNROUNDED PACE so exactly +20 is ok; null when PACE is unavailable); `reserve` (null when left is unavailable or the sampled window has already reset; out only for a FRESH zero in the current window; low for any other left <= `LOW_QUOTA_FRACTION`, a stale zero included; else ok); `even_left_pct` (= left_pct + pace_pt, null when either is missing); `exhaust_in_seconds` and `exhaust_before_reset` (from the existing projection with its own early-window guard; no second estimator); `stale` (one predicate everywhere, F8: age >= TTL, or the explicit STALE state when there is no TTL); `limited_by` and `own_left_pct` (a limited child keeps its own value); and the effective `left_pct`, `pace_pt` (unrounded), `reset_in_seconds`, `measured` that the parent rule yields (the parent's LEFT and PACE, the nearer of the two resets, the worse state). Every fact falls back on its own: `17/—`, `—/1d10h`.
(b) `pace_gaps(healths)` reads only those results (`pace_pt`, `measured`, `stale`) and returns the balance facts of M9.
Tests: boundary cases -10, exactly +20, just above +20, PACE unavailable; stale equals TTL; a zero sampled just before the reset and read just after it (state reset, reserve null); a STALE state without TTL and a zero (never `out`); zero fresh vs stale; a child with its own 26% under a parent at 8% (state blocked when the parent is out); one fixture rendered by compact, expand, plan text and plan JSON must agree.

Tests: the 17% at +3.8 fixture has no warning colour; the monochrome snapshot differs for +19.9 and +20.1; the same state words in compact and expand.

## M10 Whose process is it (caller ownership)
Purpose (owner request): an AI that sees asks in `diag running` must tell mine from another session's from facts, not guess; the behaviour "I did not start these, I will not touch them" was right but its premise was an assumption. Evidence: F9, plus cx and ag callers record tool `?` and a label that is only the cwd folder name, so labels collide. Reason: a three-valued relation to the reader (mine, other, unknown) never claims ownership it cannot prove; matching on label, cwd or batch ID alone was rejected (two agents in one repo, reusable batch IDs).
Decision:
- `diag running` (text and JSON) shows the stored caller facts (tool, label, session, owner, batch, task, cwd, workspace, ask pid) and a `relation` (mine, other, unknown) with a `relation_basis`, computed by a pure helper in `caller.py` from the reader's own `detect_caller()` and the row.
- New optional field `owner` in the caller detail (additive; the schema number stays) from the env `PEERHUB_OWNER` (validated like `session`). Precedence, first applicable rule wins: (1) host or pid namespace both known and different: other; (2) `owner` both present: equal mine, different other; (3) `session` both valid: equal mine, different other; (4) otherwise unknown. A token is the declared identity, so it must be unique per session: never set it in a shell profile or share it between two sessions (the explain topic says so). `mine` means: started by this session or by a process this session launched. An ask nested inside a provider run inherits the session's `owner` and `session` and is therefore `mine`: it is part of the session's work, the session must count it in its load and may manage it. The batch variables are stripped (F10) because they group the tasks of a batch, which is a different concept from identity; no identity variable is stripped, so no provider behaviour changes. Label, cwd, batch, task and workspace are shown but never decide.
- `load:` (diag --plan) and `active now` (batch run --dry-run) keep the store-wide total and, when any ask is not mine, append the split from one shared aggregation: `active 6/4 (mine 2, other 1, unknown 3)`; JSON `active_by_relation`.
- A reader with neither owner nor session sees `reader: unidentified (export PEERHUB_OWNER=<unique token> to classify asks)` once in `diag running`.
- Documentation lives in `peerhub explain caller-ownership` (indexed), one line in `AGENTS.md` and README (the guide is full at 1,600 bytes): export a unique `PEERHUB_OWNER` per session, a readable `PEERHUB_LEAD`, and `PEERHUB_BATCH_ID`/`PEERHUB_BATCH_TASK` for lanes; for `other` and `unknown` asks only observe and report, never stop them or reuse their stream.
- The human monitor RUNNING is unchanged.
Tests: an ask nested in a provider run (the same `owner`/`session` in its environment) is `mine`, and one with another owner is `other`; two readers on one store see the same asks with reversed relations; same folder label and different owners: other; batch IDs equal but owners unknown: unknown; equal owners with different sessions: mine (rule 2 wins); host mismatch: other; the split agrees in `diag --plan` and `batch run --dry-run`; the explain topic carries the non-interference rule; the guide stays at most 1,600 bytes.

## G Column grammar (owner request 2026-11-23, three rounds, unanimous)
Request: "think the whole column grammar through; maybe give consistency around PACE" (and `LEFT/EVN`, `EXH/RESET` pair order). Rounds: `rounds/c1.md` (independent proposals), `c2.md` (attack and resolve), `c3.md` (vote); all three peers signed YES.

Verified facts: G-F1 `PACE = used% - elapsed% = EVN - LEFT` (identity): LEFT, EVN and PACE are two independent numbers plus one derived. G-F2 the owner's balance goal (cc <= ag == cx), the colour bands (-10, +20) and the gap line are all stated in PACE, never in EVN. G-F3 the same facts had three names and three PACE formats (`LEFT`/`REM`, `RESET`/`RESET-IN`/`RESETS`, `^+4`/`^+3.8pp`/`+3.8`). G-F4 the owner's live screen (rich compact POOLS) already draws a bar per row, but `_pool_bar` has no even-burn tick; only the `--expand` `_bar_quota(even_burn=...)` draws `|`: this is why "even burn is not shown" (answer to Q1). G-F5 `TARGET%/h` = left% / hours to reset, plan only.

Decisions (each: purpose / evidence / reason):
1. Two primaries, one derived. Purpose: one reading per fact. Evidence: G-F1, G-F2. Reason: showing `LEFT/EVN` beside `PACE` prints three numbers for two degrees of freedom and rounds visibly wrong (`17/21%` next to `+3.2`). Decision: the cells are `LEFT` and `PACE(pp)`; EVN is the `|` tick in the bar of compact and `--expand` (G-F4), JSON `even_left_pct`, and the legend states `0 = even burn`. Rejected: `LEFT/EVN` cell (cx's round-1 view, withdrawn after the tick answered Q1), `USED/ELAPSED` (hides the remaining quota).
2. PACE is one cell everywhere: a signed one-decimal number (`+3.8`, `-12.4`, `0.0`, never `-0.0`), no arrow glyph (the sign carries it; the state glyph stays a STATE concern), the unit in the header `PACE(pp)`, a trailing `!` only in the rest band; the bands use the unrounded value (exactly +20 is ok). Purpose: one rendering in compact, `--expand` and `diag --plan`. Evidence: G-F3; integer `+20` would be shown for both +19.8 (ok) and +20.3 (rest). Rejected: integer in the monitor, `pp` per cell.
3. One pair grammar: `my value / its reference`, used only where no column carries the difference: `EXH/RESET` (`20h/1d10h!`, `!` when the first is smaller). The gap line stays a list of signed PACE differences, not a pair. `LEFT/EVN` is no longer a pair (decision 1).
4. Monitor and plan use `LEFT`, `PACE(pp)`, `EXH/RESET` in that order. Compact and `--expand` share one row formatter. Compact includes limited-child rows and draws the bar when it fits. `--expand` gives the bar more room and adds AGE and the other child rows. The fixed-width bar yields first. The data columns drop in order of AGE, FAMILY, then EXH/RESET. STATE, LEFT and PACE stay.
5. `TARGET%/h` is renamed `BUDGET%/h` in the plan text (the average rate that lands at 0% on reset; not a ceiling, not the owner's "target pace"); JSON `target_pct_per_hour` stays. Rejected: `MAX%/h` (reads as a hard cap), `ALLOW%/h` (reads as a permission), keeping `TARGET` (collides with the owner's word for PACE).
6. JSON: no aliases (they double three numbers per row for the AI view); old keys keep their names; new keys follow the existing suffixes: `even_left_pct`, `exhaust_in_seconds`, `exhaust_before_reset`, plus the `health` and `gaps` objects above.
7. One `!` glyph, the column says which alert: `LEFT` at or below 10% (low reserve), `PACE` in the rest band, `EXH/RESET` early. A tied or unknown forecast gets no flag. Rejected: three glyphs (a symbol table to learn).
8. One legend line below the pool block and gap line, one code constant, rendered by compact and `--expand`, checked against the docs by a test; wording: `PACE(pp)=EVN-LEFT, 0=even burn (|), <=-10 spend, >+20 rest! | EXH/RESET ! = early`. Defect found in the vote and fixed here: the legend must define EVN (even-burn remaining) so that `PACE = EVN - LEFT` is not misread as used-based.
9. Plan header: `PEER POOL LEFT PACE(pp) EXH/RESET BUDGET%/h ACTION REASON` (STATE and FAMILY are not in the token-light plan); compact header: `STATE LEFT PACE(pp) EXH/RESET FAMILY` after the bar.
Tests: header, cell and legend strings come from one constant per table; compact and `--expand` rows have equal cells; `-0.0` clamps to `0.0`; the bar tick exists in compact and `--expand`; `+20.0` is ok and `+20.3` is rest.
