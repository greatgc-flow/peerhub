# 컨텍스트 연속성과 토큰 효율 (2026-10-09)

질문: 네이티브 세션 제어(재개·중단·조종)가 필요한가, 아니면 매번 제한된 컨텍스트를 새 세션에 주입하는 현재 설계가 맞는가.
방법: ag·cx 독립 의견 → 상호 반박 → cc 직접 측정과 공식 문서 조사. 결론은 아래와 같다.

## 결론
- 기본은 **Records + 제한된 catch-up + 새 세션**을 유지한다(출처 보존, 숨은 상태 없음, 컨텍스트 부패 방지).
- 재개는 모델 입력 토큰을 줄이지 않는다. API는 상태를 갖지 않으므로 CLI가 이전 대화를 매번 다시 보낸다. 차이는 **가격**(프롬프트 캐시)뿐이다.
- 중단(취소)은 토큰이 아니라 지연, 쓸모없어진 작업 중단, 부작용 방지가 목적이다. 구현했다(프로세스 트리 종료, 종료 관찰).
- 조종(steer)과 네이티브 재개는 구현하지 않는다. 사용량 측정으로 이득이 확인되면 cc·cx에 한해 스레드별 명시적 선택 기능으로 검토한다. ag는 백엔드 TTL·과금 계약이 확인될 때까지 보류한다.

## 측정 (haiku, 약 3만 토큰 문맥, 같은 질문)
- 재개와 새 세션 모두 매 턴 약 3만 토큰이 입력된다.
- 캐시가 따뜻할 때 턴당 비용: 재개 약 $0.0037, 새 세션 주입 약 $0.0216(약 5.8배). 새 세션은 주입한 약 9.6k 토큰을 매번 캐시에 새로 쓴다(쓰기 1.25배, 읽기 0.1배).
- 이득은 캐시 유효시간 안에서만 유지된다(Anthropic 기본 5분, 구독 메인 대화는 1시간). 간격이 길면 재개도 전체를 다시 쓴다.
- Codex 새 세션은 같은 앞부분이면 자동 캐시로 적중이 0~99%로 들쭉날쭉했다.
- CLI 고정 부담은 새 세션당 입력 약 1.4만(Codex)~2.5만(Claude) 토큰이며 재개 요청에도 붙는다.
- 대략 "따뜻한 재개 이력 × 0.1 < 새로 주입하는 catch-up 크기"일 때 재개가 유리하다.

## 이번에 반영한 것
1. 요청별 사용량 기록: `ask --json`의 `usage`와 응답 Record 메타데이터(`input_tokens`, `cached_input_tokens`, `cache_write_tokens`, `output_tokens`; CLI가 보고하지 않는 값은 0이 아니라 생략).
2. catch-up 프롬프트에 기록 위치·ID·종류를 넣고, 잘렸으면 첫 줄에 생략 안내를 둔다. 현재 질문은 맨 마지막.
3. 기본 catch-up 예산에 24,000바이트 상한을 추가(ag의 Windows 인라인 한도 30,000바이트 안쪽).
4. `control.cancel`을 프로세스 트리 종료로 구현(`supports_terminate`). 죽인 뒤 진행 중이던 전달은 정상 응답으로 끝나지 않는다.

## 후속 후보 (측정 후)
- 접두사 안정 배치: 고정 지침 + 버전 있는 체크포인트(요약 Record) → 바뀌는 최근 기록 → 현재 질문. 슬라이딩 윈도우는 앞부분이 바뀌어 캐시를 무효화한다.
- 2·10·50턴, 캐시 유효시간 전후 간격으로 새 세션 vs 재개를 쌍으로 측정(입력·캐시 읽기/쓰기·출력·지연·파일 변경 시 정확성).
- 구독 쿼터는 API 비용 환산과 별도로 측정한다.
