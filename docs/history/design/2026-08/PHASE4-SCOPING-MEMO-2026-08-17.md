# Phase 4 Scoping Memo: Shadow Validation

## 1. Actual Dispatch Entry Points Today
The primary dispatch entry point is `action_ask` (defined at `P:\_sys\core\hub.py:6005`). This function applies a governed-mutation guard and wraps the core execution logic in `_action_ask_inner` (`P:\_sys\core\hub.py:6154`). 

To observe a real dispatch without altering `hub.py`'s behavior or timing, a "shadow" tap should sit inside `_action_ask_inner`, specifically right after the adapter prepares the input command and payload (around line 6720 with `prepared = prepare_input(...)` and line 6741 `cmd = list(prepared.argv)`). Tapping here, just before the blocking `_ask_with_pty` (line 6856) or `_spawn_process` (line 7135) calls, allows the tap to capture the fully resolved target (`to`), profile routing decisions, session keys, and exact command arguments without affecting the actual dispatch execution.

## 2. Ownership-Cluster Routing
Ownership-cluster routing conceptually requires a deterministic identifier that maps a request to a specific session or owner context. 
`hub.py` currently possesses this capability natively. Inside `_action_ask_inner` (line 6662), it calculates a `scope_key` (`base_scope = _compute_scope_key(ai_root, explicit_scope)`) and uses it to resolve an active session (`existing_session = _get_active_session(health_peer, scope_key)`). This `scope_key`, or the resulting persistent `session_id` (line 6697), acts as the precise per-request owner/room identifier needed to tell the shadow layer which dispatches belong to which cluster.

## 3. Same-Revision Comparison
To ensure `hub.py` and `peerhub` produce directly comparable output, they must process the same inputs and have their outputs evaluated identically.
- **Inputs:** `peerhub` needs the exact `cmd`, `process_env`, and `query` payload generated by `adapter.prepare_input()` (line 6720) in `_action_ask_inner`.
- **Outputs:** `hub.py` relies on `adapter.parse_output(raw_text, node)` (lines 6870, 7207) to extract the final output, and `adapter.extract_usage(...)` (lines 6977, 7168) to track tokens. 
New plumbing will be required to pipe the final `output` string, `exit_code`, and `usage` dictionary from `hub.py` back to `peerhub` for comparison, as there is currently no mechanism exporting these final evaluated values out of the process once the subprocess finishes.

## 4. Instant and Lossless Shadow Path Disablement
`hub.py`'s request lifecycle is entirely synchronous. Once `_action_ask_inner` initiates process execution via `_ask_with_pty` (line 6856) or `_stream_process_output` (line 7149), it blocks the thread until completion. 
Disabling the shadow path would be "instant and lossless" if the shadow tap operates purely as a fire-and-forget payload copy (e.g., via a non-blocking queue, UDP, or detached process) dispatched immediately before the synchronous block. Because `hub.py` maintains no internal asynchronous event loops or in-flight queues for the ask, and commits no state until the subprocess exits, bypassing a stateless shadow tap introduces no stranded data or abandoned promises on the primary `hub.py` path. 

## 5. Open Questions for the Real Design Pass
- **Transport Mechanism:** How will the shadow tap asynchronously transport the fully prepared payload (`cmd`, `query`, `process_env`, `scope_key`) to `peerhub` without blocking or introducing latency into `hub.py`'s synchronous `_action_ask_inner` thread?
- **Output Hook Integration:** How and where will `hub.py` transmit its post-execution results (the parsed `output` and `exit_code`) to `peerhub` for the "same-revision comparison"? (e.g., a post-execution hook immediately before `pending_success = _PendingAskSuccess(...)` at lines 7071 / 7273).
- **Concurrency & Session Mutation:** Since `peerhub` will be processing the same `session_id` traffic concurrently with `hub.py`, how will we prevent or isolate `peerhub` from causing session fingerprint drifts or locking conflicts on the shared `.ai\state.json` or `.ai\sessions\` persistence layer?
